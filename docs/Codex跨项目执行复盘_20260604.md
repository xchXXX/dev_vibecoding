## 总体结论

从当前证据看，问题不是单点失误，而是集中分布在以下几类：

- Windows 命令与 PowerShell 兼容问题反复出现。
- 用户偏好无法跨线程稳定继承，需要用户重复纠正。
- 长任务执行顺序在默认情况下并不稳定，必须靠规则和黑盒评测不断加固。
- 工具来源选择不稳定，尤其在“会话内置能力 vs 脚本/API”上容易偏航。
- 许多规则目前仍以 prose 为主，尚未全部转成强约束闸门。

换句话说，当前主要瓶颈不是“缺更多规则”，而是：

- 缺更强的用户偏好真源。
- 缺更强的流程硬闸门。
- 缺更稳的 Windows 命令兼容层。
- 缺跨项目统一复盘与观测面板。

## 一、经常执行错误的内容

### 1. 命令报错类

#### 1.1 Windows / PowerShell 兼容与引号问题

这是最稳定、最反复的一类问题。

证据：

- `C:\Users\72385\.codex\memories\command-failure-memory\index.json` 中多条 case 的 `scope_reason` 直接指向 PowerShell 5.1、rules helper、CLI wrapper、escaping、binding behavior。
- 本次复盘过程中也复现了同类问题：混合 repo/home 路径的 `rg` 扫描在 PowerShell 引号下被错误拆解。
- `codex-tui.log` 中存在多处 `ParserError` 记录。

表现形式：

- 命令字符串在 PowerShell 下被错误分词。
- `.cmd -> .py -> .ps1` 兼容入口在不同 shell 环境下行为不一致。
- heredoc、引号嵌套、正则表达式、远程命令拼接容易出错。
- 同一命令在 CLI、桌面线程、子代理窗口中的行为不完全一致。

本质问题：

- 运行层缺统一的 Windows 命令兼容约束与模板。
- 很多命令仍依赖临时拼接，而不是稳定包装器。

#### 1.2 ghost snapshot / Git 索引异常

这是另一类明显重复出现的问题。

证据：

- `codex-tui.log` 中 `unable to index file 'NUL'` 至少出现 `17` 次。
- 同一错误反复伴随 `failed to capture ghost snapshot`。

表现形式：

- ghost snapshot 触发时，`git add --all` 因 Windows 特殊文件名 `NUL` 失败。
- 失败虽然多数时候不阻断主任务，但会不断制造噪音和误导。

本质问题：

- ghost snapshot 对 Windows 特例处理不完整。
- 当前链路没有针对 `NUL` 这类保留名做前置过滤或降级。

#### 1.3 环境预检缺失

证据：

- `history.jsonl` 中明确出现 `jupyter 不是内部或外部命令`。
- 多处运行留痕中出现 `repo_doctor.ps1` 缺失，只能以 warning 形式跳过。

表现形式：

- 在真正开始任务前，没有先确认 `jupyter`、`pwsh7`、Python、SSH、doctor 脚本或外部工具是否可用。
- 结果是任务在中途才暴露环境缺口。

本质问题：

- 缺统一的“任务前环境探测”。
- 目前 doctor 更偏项目治理，不够偏任务执行前提。

#### 1.4 长耗时运行导致人工中断

证据：

- `history.jsonl` 中有 OCR、PDF、Notebook、模型实验等多个任务，用户多次询问是否卡住、是否异常、是否要终止。
- `history.jsonl` 中存在 `KeyboardInterrupt` 场景。

表现形式：

- 任务本身未必错误，但缺少进度证据、缺少心跳、缺少阶段判断，最终被用户视为“卡住”。
- AI 也容易在没有结构化进度的情况下做出错误判断。

本质问题：

- 长耗时任务缺统一进度可视化。
- 缺区分“慢但正常”与“异常卡住”的判定机制。

#### 1.5 第三方平台/网络类错误处理不稳定

证据：

- 历史输入中有 `TLS 握手中断`、TOS 下载问题、`InputImageSensitiveContentDetected.PrivacyInformation` 等。

表现形式：

- API 已接受任务，但下载或回收阶段失败。
- 供应商内容风控与用户期望冲突。
- 计费、模型 ID、上传方式、直传与 TOS 之间口径不统一。

本质问题：

- 缺针对外部供应商的稳定 playbook。
- 缺“平台限制知识库”与“出错时标准回退路径”。

### 2. 执行顺序错误：用户已明确声明

这类问题的特点是：用户已经明确说过，但仍需要在不同线程里重复纠偏。

#### 2.1 先回答问题，再继续手头工作

该问题后来才被沉淀成项目规则，说明默认行为并不天然稳定。

用户历史上多次是先问清楚一个问题，再决定是否继续实施；如果 AI 直接继续施工，会被视为没听懂当前优先级。

#### 2.2 先方案/施工文档，再实施

证据集中出现在 `2026-05-29` 一批规则重构与 orchestrator 改造线程中。

用户明确要求：

- 先落方案文档。
- 再落施工文档。
- 再同步核心文档与测试。
- 最后才进入实现。

这类顺序后来被项目规则、`global-task-orchestrator` 和 `tests/harness` 黑盒评测反复加固，说明默认行为会漂。

#### 2.3 先核心文档与测试，再代码实现

用户已明确强调：

- 长任务下，核心架构、模块、契约、入口与测试的同步要先于代码实现。

该要求已经被写入规则，但从“需要专门加规则和测试”本身就能反推：此前这条默认并不稳定。

#### 2.4 使用会话内置能力，不要擅自换成脚本/API

在图像生成相关线程中，用户多次明确要求：

- 使用会话内置 image 能力。
- 不要改走脚本或额外 API。

这说明工具来源选择曾发生过偏航，且给用户造成了明显负反馈。

#### 2.5 长任务不要中途汇报，做完再停

历史里多次出现：

- “不要停”
- “不要中途汇报”
- “做完所有任务后再停”

这类偏好非常稳定，但目前仍主要靠用户在每个线程重新声明。

#### 2.6 审阅与返工必须走固定路由

用户后来专门要求并固化为规则：

- 审阅交给专门审阅子代理。
- findings 必须转发给原施工子代理返工。
- 后续复审复用同一个审阅子代理。

这说明如果不额外约束，默认实现容易出现重新开并行子代理、返工上下文漂移等问题。

### 3. 执行顺序错误：用户未明确声明时的默认偏差

这类问题更关键，因为它们反映的是“当前默认行为还不够稳定”。

#### 3.1 默认不会稳定地自动读取正确入口文件

这是用户后来专门要求做黑盒评测的重点。

说明问题：

- 在不提醒规则的情况下，Codex 未必会自动读取 `AGENTS.md`、`RULES_ENTRY.md`、`RULES_INDEX`、目标路径相关文档与 skill。
- 也未必按预期顺序读取。

#### 3.2 默认不会稳定地执行“失败记录 -> 查询 -> 重试 -> 回写”

虽然 `command-failure-memory` 在 blind 子代理 benchmark 中已做到 `10/10`，但：

- `docs/ai/runs/2026-04-21-command-failure-memory-blind-benchmark.md` 明确指出 Windows CLI blind forward-test 仍可能在首个失败 shell 回合卡住。

这说明：

- 子代理窗口里的自动触发率已经较高。
- 但 CLI 路径和某些执行环境的默认行为仍不稳。

#### 3.3 默认不会稳定地区分“问题型请求”和“实施型请求”

历史里可以看到两类用户不满：

- 想先听分析，AI 却开始动手。
- 想直接实施，AI 却停留在分析或来回确认。

本质是意图分类还不够稳定。

#### 3.4 默认不会稳定地区分项目规则与全局规则

`2026-05-29` 到 `2026-06-04` 的多轮讨论都围绕：

- 这是项目级，还是全局级。
- 项目规则和全局规则冲突怎么办。
- 文件放在哪里才算合理。

说明作用域判定是一个持续性的易错点。

#### 3.5 默认不会稳定维持用户长期偏好

例如这些偏好都具有跨线程稳定性：

- 说明性内容默认中文。
- 不要中途打断长任务。
- 实施前要有明确方案。
- 图像生成优先用会话内置能力。
- 不希望 AI 每一步都频繁汇报。

但当前它们没有形成稳定、可执行的用户级真源。

## 二、哪些流程和内容可以优化

### 1. 用户偏好管理

当前最需要优化的不是再写更多规则，而是把高频用户偏好从“聊天里重复说”升级为“机器可检索真源”。

应沉淀的用户长期偏好至少包括：

- 默认中文说明。
- 问题优先回答。
- 长任务前先方案。
- 静默长跑模式可选。
- 会话内置工具优先。
- 长任务不喜欢频繁汇报。
- 更偏向直接落地，不希望停留在泛泛建议。

建议新增：

- 用户偏好档案。
- 线程内显式覆盖字段。
- 项目级与用户级偏好的合并顺序。

### 2. 执行顺序治理

长任务顺序虽然已有规则，但还应继续从 advisory 走向 executable gate。

需要硬化的步骤：

1. 识别是否为长任务。
2. 长任务强制生成方案文档与施工文档。
3. 强制同步核心文档与测试。
4. 强制记录子任务与审阅路由。
5. 审阅通过前不允许正式收口。

应避免继续依赖：

- 只在 prose 中要求。
- 只靠主协调器“记得这么做”。

### 3. 工具来源选择

图像生成、视频生成、脚本调用、第三方 API 等任务里，最容易出现“做成了，但方式错了”。

建议建立工具来源优先级：

1. 会话内置能力。
2. 已安装且适配的 skill。
3. 仓库内固定脚本。
4. 明确授权的外部 API。

并为以下场景建立专门闸门：

- image/video 生成。
- 供应商 SDK/API。
- 远程 SSH/服务器操作。
- 本机环境安装与配置。

### 4. 长耗时任务体验

当前长耗时任务的核心问题不是一定失败，而是“用户感知像卡死”。

建议优化：

- 引入结构化心跳，不一定发给用户，但要写事件。
- 区分 quiet 模式与 normal 模式。
- 长耗时任务默认写阶段状态：
  - 已开始
  - 正在跑哪个批次/第几步
  - 最后一次有效进度时间
  - 是否检测到异常

### 5. 第三方平台集成流程

Seedance、TOS、图片生成、内容风控、计费等问题已经说明：

- 单次临时排查成本很高。
- 同类问题后续还会再来。

建议做成固定 playbook：

- 上传方式决策树。
- 平台风控限制说明。
- 失败任务回收与重试策略。
- 下载异常的排查顺序。
- 计费查询入口与核对方法。

### 6. 复盘与观测流程

当前复盘要分别读取：

- `history.jsonl`
- `session_index.jsonl`
- `.codex-global-state.json`
- `codex-tui.log`
- `docs/ai/runs/*`
- `docs/ai/tasks/*`
- `command-failure-memory`

这说明目前缺统一观测面。

建议建设：

- 跨项目复盘索引。
- 按 thread 聚合的摘要视图。
- 用户纠偏语句自动抽取。
- 高频错误聚类。

## 四、从最新 harness 环境视角，还需要改进什么

### 1. 规则系统已经比过去强很多，但还不是完整流程操作系统

当前已经具备：

- 项目级 `rules/registry/*`
- `rules/items/<kind>/*`
- `global-task-orchestrator`
- `command-failure-memory`
- `sync-codex`
- `doctor`
- blind benchmark

这是正确方向。

但仍存在的问题是：

- 许多约束还是“写出来了”，不等于“强制执行了”。
- 许多测试还是验证结果，不是验证整个过程顺序。

### 2. `global-task-orchestrator` 已经明显简化，但还缺可视化总览

当前三件套：

- `state.json`
- `task.md`
- `events.jsonl`

相比旧控制面已经大幅收敛。

但还缺：

- 一个统一总览页。
- 当前 phase、子任务、阻塞、审阅状态的摘要视图。
- 便于跨项目回顾的历史索引。

### 3. `command-failure-memory` 很有价值，但现在仍偏“命令故障记忆”

已验证的优点：

- blind 子代理窗口自动触发率高。
- 失败 -> 查询 -> 重试 -> 回写 闭环已可执行。

但仍不足：

- 只覆盖命令层失败，不覆盖更高层流程失败。
- 不会自动把“用户纠偏”沉淀成流程记忆。
- CLI 路径在 Windows 上还不够稳。

### 4. blind benchmark 要继续扩张

当前 blind benchmark 已证明一个重要方向：

- 真正有价值的不是“文档写得好不好”，而是“不提示时 AI 会不会自动做到”。

后续应继续黑盒评测：

- 是否自动读入口规则。
- 是否自动区分问题与实施。
- 是否在长任务中先落方案/施工文档。
- 是否 quiet 模式下不乱汇报。
- 是否在诊断模式下不越界修改。
- 是否稳定复用同一审阅/返工路由。

### 5. 跨项目统一观测仍是最大短板之一

当前想回答“所有项目里到底反复出什么问题”，仍然需要手工拼装多个来源。

这说明需要新增：

- thread 汇总索引。
- 纠偏标签。
- 高频错误标签。
- 项目/时间/任务类型维度筛选。

没有这个层，很多优化只能靠记忆和人工印象推进。

## 五、建议的优先落地顺序

建议后续实施顺序如下：

1. 先做用户偏好真源。
2. 再做长任务顺序硬闸门。
3. 再做 Windows 命令兼容层。
4. 再做 diagnose-only 与 quiet long-run 模式。
5. 再做跨项目复盘索引与观测面板。
6. 最后扩展 blind benchmark 覆盖面。

这样排序的原因：

- 这几项直接对应历史中最常见、最让用户反复纠偏的问题。
- 它们能同时改善多个项目，而不是只修一个局部场景。

## 六、最终判断

本次复盘得到的最核心结论不是“Codex 经常做错很多零散小事”，而是：

- 当前系统缺少一层稳定的“用户长期偏好 + 流程硬闸门 + 跨项目观测”。

只要这三层没有补齐，就会持续出现以下现象：

- 同样的偏好在不同线程反复重申。
- 同样的顺序要求反复靠人工纠偏。
- 同样的 Windows/CLI 兼容问题反复踩坑。
- 同样的长任务体验问题反复出现。

因此后续优化方向应从“继续加更多文字规则”转向：

- 更强的真源化。
- 更强的自动判别。
- 更强的执行闸门。

# 方案编制与交接

本页是 GTO 方案内容、呈现和交接材料的唯一正文。仅用于用户显式选择 GTO 的任务；阶段、职责与返工门禁见 [任务流程与职责](workflow.md)，实际初始化和校验见 [控制器指南](controller-guide.md)。

## 每个任务如何呈现

Plan 默认只展示四块：施工摘要、改造要点、施工流程和任务表。简单任务直接沿用[通用施工图](workflow.md#通用施工流程图)；存在多个实施分支、特殊依赖或适用步骤变化时，再展示本次任务图。任务图只展开本次节点和依赖，Review/验收回路引用 [任务流程](workflow.md#回路与阶段出口)，不复制另一套返工规则。

施工摘要先用一小段话说明当前问题、建议变化、可观察结果与主要取舍；范围、验收和风险紧随其后，只有便于比较时才用表格。改造要点按最终结果分组，用“当前问题 → 改动位置与处理规则 → 为什么有效 → 验收实例”讲清实现因果。完整要求保留稳定编号，关联责任与验收；长清单放在正文后的详细核对区，支持折叠时才折叠。影响批准的关键机制、条件、风险和待决定事项必须在正文可见。遗漏、排除或尚不能落实的要求必须说明并取得确认。确认后 `state.json` 保存唯一机器合同，`plan.md` 展示同源视图；其他工件只承担分工、验证和导航，不独立维护第二份要求。

### 呈现媒介与阅读检查

| 要表达什么 | 优先媒介 | 使用边界 |
| --- | --- | --- |
| 建议、因果、取舍和风险 | 短段落 | 一段解释一个关键判断，避免只列“同步、收敛、整合” |
| 改前改后、方案或情况比较 | 对照表 | 长解释留在表外 |
| 系统输入、判断、处理、输出 | 处理流程图 | 解释系统如何工作，不混入施工角色 |
| 并行、串行、汇合和前置门槛 | 施工图 | 按同一任务依赖生成或核对，不另维护相反的顺序 |
| 页面变化 | 标注截图或内容原型 | 区分拟议效果与已运行事实 |
| 分工与交付 | 四列任务表 | 显示计划代理和职责，不能只写“测试者/验收者” |
| 字段、路径、命令与完整证据 | 详细核对区 | 给明确入口，关键结论仍在正文 |

正文读完应能回答：改完有什么不同、怎样实现、为什么选它、失败时怎么办、怎样证明、哪些仍待确认。结构检查不能证明阅读效果；用小修复、普通功能、复杂并行改造的实际样例试读，样例见 [Plan 阅读示例](plan-reading-examples.md)。不要把同一段文字同时塞进摘要、图和表。

固定复用：先确认后落盘、先控制面后实施、文档与测试先行、整合后的独立审查和真实验收、按问题来源分开的返工回路、事实收尾。每次重新确定：子任务数量与目标、职责、依赖、并行关系、修改边界、交付物、验收操作和必要环境准备。不是只替换代理名字。

任务表默认只显示四列；机器边界和子代理提示所需的详细字段仍进入同一合同，不在 Plan 主表重复铺开。

| 列 | 写到什么程度 |
| --- | --- |
| 步骤 | 稳定编号，必要时带阶段 |
| 责任 | 计划代理代号及职责；同代号明确复用，真实 ID 在 Execute 创建后绑定 |
| 交付 | 目标行为、交付物和关键证据 |
| 前置条件 | 依赖、并行关系及开始门槛 |

### Plan 首次输出合同

Plan 首次向用户交付方案时，必须同时给出以下可核对内容；缺任一项都不能请求批准：

1. 施工摘要：目标、范围、不做、实施方式、验收和主要风险。
2. 改造要点：覆盖此前要求和后续修正，按结果分组并关联责任与验收。
3. 施工流程：引用 [任务流程](workflow.md#通用施工流程图) 的唯一通用流程；复杂任务另给本次任务 DAG。
4. 任务表：只展示步骤、责任、交付和前置条件。
5. 两条来源回路：Review 来源由原 Reviewer 发现并复审、原整合者修复；验收来源由原验收者发现并复验、原整合者修复。

默认不展示内部 revision、工具绝对路径、schema 字段或控制器命令；只有这些信息影响用户选择、迁移或故障判断时才说明。

需要机械核对时，将同一内容表示为 `validate_plan_output_contract(value)` 的语义对象。内部 `six_points` 仅承载施工摘要的六类值，不要求向用户显示“六要点合同”；`requirements`、`workflow` 和 `tasks` 分别承载改造要点、唯一流程与任务表。该对象只服务批准前核对，不进入 state，不新增持久化字段。

## 批准与交接

Plan 在请求批准前核对完整要求、分工、依赖、写入边界和验收覆盖，按 [批准分工与依赖](workflow.md#批准分工与依赖) 核对代理复用及独立性。批准后先按 [控制面前置条件](workflow.md#适用范围与施工前置条件) 及 [初始化入口](controller-guide.md#六要点合同) 创建、校验同一任务六工件；不委派实施者提前交付。

交接给 Execute 的提示只提供：消费项目和既有任务摘要入口、已批准范围、当前进度与真实阻塞、下一步动作及必要证据入口。Execute 从摘要恢复同一 state；任务职责和恢复门禁见 [任务流程](workflow.md#阶段职责与暂停恢复)。同窗口继续也使用同一交接内容，不重新初始化。字段与样例从 [状态合同](state-schema.md) 及同包 JSON 示例按需读取，不在提示中复制一份独立可编辑合同。

## 范围复验变更入口

现行行为与版本边界见[按验收点保留结果与范围复验](acceptance-points.md)。首次验收可分范围登记；保留任意历史轮次中仍有效的结果，最终检查完整覆盖，不要求额外整轮全绿。普通任务使用简洁清单，只有显式选择 GTO 才使用控制面。

## 恢复与登记精简

新增恢复摘要、精确工具入口、原始证据登记草稿及无文档差异的事实收尾，合同唯一见[恢复、登记与收尾](streamlined-execution.md)。现有安全门禁和旧冻结版本保持；新增入口仅适用于包含它们的运行包，实际安装以发布回执为准。

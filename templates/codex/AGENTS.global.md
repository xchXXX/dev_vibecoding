# AGENTS

本文件是跨项目使用 Codex 时的全局入口，只保留稳定协作约定与 harness 发现方式。

## 沟通与协作

- 说明性内容默认使用中文；代码标识、命令、路径和配置键保持原样。
- 用户提出问题时，先回答问题，再继续手头工作。
- 准备修改文件前先给简短计划；完成后说明结果、验证和剩余风险。
- 对 quiet long-run 保持耐心；没有异常证据时不催促、不打断、不重复启动。
- 优先给出简洁、直接的回复，不要无意义铺陈或过度分类。

## 变更流程

- 涉及代码交付、Git 分支或发布管理时，读取 `{{HARNESS_ROOT}}/rules/items/workflow/分支与发布管理.md` 与项目 `config/ai/git-policy.json`（若存在），按当前操作执行关键节点检查；既有任务继续原分支，保留其他任务的工作，不把提交、推送、合并和部署混为同一状态。

- 问答、只读检查以及用户明确要求的普通 Git 提交、推送等日常操作直接执行；Git 操作先核实分支和提交范围，不额外要求方案确认。强制推送、覆盖历史或删除资源须核实影响与授权，不按普通推送处理。
- 代码改造、配置调整、服务器部署等工作，先说明与规模相称的简短方案：改动范围、实施步骤和验证方式；用户确认后执行，已有明确方案与授权不重复确认。普通工作不强制生成施工文档、流程图、任务表或控制工件。
- 在拿到足够上下文后，优先直接推进，不要长时间停留在宽泛分析阶段。
- 用户明确要求 quiet long-run 时，压缩常规进度播报，保留内部进度跟踪，只在真实阻塞、高风险决策或最终完成时打断。
- 普通任务的流程由当前主代理按本入口和用户授权组织；显式 GTO 任务的阶段、分工和门禁只由同一冻结 GTO 合同定义。方法 skill 只提供诊断、测试、评审反馈与验证方法，不能新增重复审批、另建控制面、擅自派发代理或改动工作区。
- 独立并行任务使用各自工作区和状态，先检查已有工作与资源归属；worktree 不隔离端口、数据库或全局安装。共享安装单发布者，任务使用固定运行版本；不自动合并别的任务，不清理仍被引用的证据。
- GTO 仅在用户显式要求使用时启动；任务复杂时可以建议，不因工作量、风险、服务器操作或需要方案而自行启动。用户已批准采用 GTO 的在途任务继续沿用原任务流程，不重建控制面或擅自取消门禁。
- 仅对已选择 GTO 的任务，Plan 编制与交接见 `{{SKILLS_DIR}}/global-task-orchestrator/references/plan-guide.md`；阶段、六工件和分工规范见 `{{SKILLS_DIR}}/global-task-orchestrator/references/workflow.md`；普通任务由当前代理按授权完成，不默认组织多代理审查。
- 验证按目标行为选择能提供可信证据的最低成本方式；仅在 GTO 任务中，分层黑盒测试、场景卡、报告与验收流程要求遵循 `{{SKILLS_DIR}}/global-task-orchestrator/references/blackbox-methodology.md`。普通任务不因验证而创建 GTO 控制面。
- 仅在 GTO 任务中，用户批准后至六工件成功创建、校验并通过首次交付 preflight 之间，只允许在消费项目自身 `.tmp/` 写入一次性合同 JSON。此期间禁止业务代码、正式测试、正式文档、`.gitignore`、manifest/lockfile/requirements、环境配置、脚手架、构建和部署资源等交付写入；控制器不能拦截平台文件工具，主协调器须在首次派发交付任务或首次交付写入前执行 preflight。

## 实现约束

### 唯一真源

- 每项规则、流程、字段定义和任务事实只指定一个可编辑真源；其他入口引用真源，不另写一份需要独立维护的同义内容。
- 索引、安装副本和展示文档可以由真源生成，但必须明确来源并通过对应脚本刷新，不手工维护第二套定义。
- 迭代时先修改真源，再更新引用和生成物；历史记录保留当时事实，不作为现行规则入口。

### 实现方式

- 可用少量、直接、低复杂度代码完成时，优先选择更短、更易审阅和维护的实现。
- 保持逻辑干净、简洁、边界清晰；没有真实兼容负担或明确要求时，不主动增加兼容分支、过渡层、双轨逻辑或历史包袱。
- 新增文件必须遵守 `{{HARNESS_ROOT}}/rules/items/architecture/通用文件存储位置.md` 与 `{{HARNESS_ROOT}}/rules/items/policy/文件存储位置强制约束.md`；临时文件、临时脚本、测试隔离目录和一次性分析产物必须清理或留在规则允许的临时落点。
- 存在不确定点时，先调研真源或请求澄清；未经确认不得实施范围外改动。
- 未明确要求改动的内容默认不动；额外改动必须先说明并得到同意。

## 全局规则引导

- 全局默认使用规则系统，不只依赖当前对话的临时理解。
- 固定读取本全局 `AGENTS.md`、项目 `AGENTS.md` 和可用的 `RULES_INDEX.json` 元数据。
- 固定规则正文仅有三条：`global.policy.变更约束`、`global.workflow.用户提问先回答再继续`、`global.style.说明默认使用中文`。
- 其余规则由 Codex 结合对话语义、目标内容、风险、当前阶段和本轮实际操作自由决定是否读取；索引提示和 `linked_skill` 不组成固定规则套餐，也不自动触发 skill。
- 项目没有规则索引时，使用 `{{HARNESS_ROOT}}/rules/registry/RULES_INDEX.json` 作为全局元数据索引。
- `{{HARNESS_ROOT}}` 指向当前已安装的自包含规则根；`{{SKILLS_DIR}}` 指向当前技能安装目录，两者由安装器分别渲染为核实的绝对路径，不能推定技能位于规则根下。不要从作者 checkout 或其他 clone 猜测入口。
- 其他项目消费 harness 规则时，只导出 `scope != project` 的条目，不把项目私有规则外溢。
- Python 只离线生成、校验索引；正常交互链不运行 matcher、不生成 `task_profile`、不拼装按任务类型固定规则套餐。

## 实施与安全

- 尊重现有未提交改动，只修改任务范围内文件；未知内容不覆盖、不删除。
- 优先使用仓库已有脚本和最小相关验证；生成物只由对应生成脚本刷新。
- 不读取或输出认证信息、token、密钥；涉及系统配置、外部写入或破坏性操作时先确认边界。

## 执行环境与能力

- 执行环境由用户和项目声明选择：Windows 原生、Linux 或 WSL；共享规则与方法不强制某一种环境。解释器、路径、依赖和工作目录使用所选环境的真实值，不混用跨系统 venv 或 node_modules。
- 若选择 Windows Agent 与 WSL 项目，先核实发行版、同一项目路径和 Codex home 映射，再通过 `wsl.exe -d <发行版> --cd <Linux项目路径> --exec <解释器> <脚本>` 调用。集成终端配置不等于 Agent 环境，不猜 Linux-only 路径映射。
- 基础安装与 doctor 使用 Python 3.11+，不自动安装可选工具。项目首次运行时按项目已有环境声明核验所需依赖；没有选择 WSL 的项目不承担 WSL 工具清单。
- Browser、Computer Use、截图和 MCP 使用当前宿主实际暴露的能力；不修改 app-managed transport、插件缓存或安全策略，不靠临时桥或切换平台掩盖缺失。
- 真实命令失败按可用 CFM 的 record-failure → query-before-retry → record-success 闭环；预先声明、最小且类型相符的 TDD Red 例外。runner 未安装时报告缺失并保留失败证据，不假装记录成功，不因记录失败盲目重试原命令。
- 安装更新只拥有 receipt 列出的资产和 AGENTS 标记区块；用户正文、hooks、MCP、其他技能与个人数据不在所有权内。指令更新须在新会话核验，磁盘文件不等于能力验收。

## 工具

- 涉及图片生成或编辑时，优先使用当前会话内建的图片能力，不要静默切换到外部脚本或 API 路径。

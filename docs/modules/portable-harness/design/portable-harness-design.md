# 完整 Harness 可移植与低摩擦接入设计规格

版本：v0.1，待审阅。日期：2026-10-13。

状态：用户已选择方案 B（完整 harness 共享核心，Windows 原生与 Linux，保留 WSL），并授权隔离基线和书面规格准备。本规格及后续实施计划尚未获批；本文描述目标合同，不表示这些能力已经实现或验收。

## 1. 目标与成功定义

为同一位用户在本地与云端复用、以及其他 Codex 用户接入，提供同一个可分发核心。两类用户共用路径解耦、环境适配、安全安装、版本管理、诊断和验收；对外接入额外要求陌生用户能仅凭文档完成、许可清晰、支持范围可解释。不能先验认定这是两套产品。

R01：在声明支持、依赖已满足的环境中，接收者无需修改源码、无需作者人工指导；最多填写三项接入参数：已核实的 Codex home、技能安装位置、执行环境选择。默认值可验证时免填，不可靠时明确诊断，不猜其他 clone 或账户位置。

R02：依赖已满足且没有冲突的首次接入，主流程不超过两次 CLI 调用（安装、doctor），再新开 Codex 会话并执行示例任务。依赖准备单独计数，不能藏进“简单安装”；记录总耗时、配置项数、命令数、人工介入次数和失败恢复成本。时间先实测，不承诺未经验证的分钟数。

R03：普通任务可消费规则与方法论；只有显式选择 GTO 才进入编排流程。完整能力验收必须分别证明磁盘安装、实际会话加载、真实 GTO 流程，不能以一种证据替代另外两种。

## 2. 范围与边界

包含：规则注册表与叶子规则；pre-dev-benchmark、fix-closure-gate、command-failure-memory 和 GTO；配置与环境适配；安装、更新、卸载、回滚与诊断；完整分发包、文档和示例；Windows 原生、Linux、WSL 的相应验证。

不包含：自动迁移在途 GTO 任务、同步个人记忆、商业网站或 SaaS、多租户服务、付费系统、macOS 支持承诺、任意云平台兼容承诺、自动安装全部可选工具、改写任意 MCP/hooks/插件配置或自动发布。

“云端”首轮指明确选定且可实际验证的 Linux 执行环境；主机文件系统、持久化、Codex 技能加载和代理能力都需确认。没有真实云端入口时，将 Linux 运行验证和云端会话验证分列，后者标记阻塞。

## 3. 分层与真源

R04：区分源码层、安装层、消费项目层。

- 源码层维护规则、技能、模板、schema、适配器和测试；核心不依赖作者用户名、固定盘符或个人配置。
- 安装层是带版本清单的自包含副本，不引用作者开发 checkout。源码目录移动后，既有安装仍应可用。
- 消费项目提供项目覆盖、业务代码及其任务证据；不要求先改造业务目录结构。项目侧控制工件仍按已批准的 GTO 合同保存。

当前主版 GTO 与 standalone 是独立维护副本。实施应先比较差异和保留独有可移植行为，再形成一个共同真源及可重复生成的分发内容；不得直接用任一副本覆盖另一副本。是否继续提供精简 GTO 包可由同一生成入口表达，不形成第二套控制器实现。

环境差异限制在明确适配层：路径表示、锁、子进程/超时清理、可执行文件解析、控制台编码、安装路径。方法论、状态 schema 和业务规则不按操作系统复制。

## 4. 配置合同

R05：配置优先级为内置默认值、用户配置/受控环境变量、项目允许覆盖项、显式 CLI 参数。每一项需声明类型、默认、允许来源及解析来源；同层冲突不得静默吞掉。具体字段名在实施计划前冻结。

项目配置不得覆盖全局安装目标、信任/所有权边界或其他用户目录。路径相对包含该路径的配置文件解析，不依赖启动 cwd；规范化后检查越界、符号链接/重解析点和大小写冲突。错误字段和未知字段给出可执行诊断。

Codex home 与技能目录分别处理；环境变量只是候选输入，仍需核实。WSL/Windows 路径转换只接受已确认映射。配置不承载密钥、令牌或凭证；诊断只输出允许公开的字段和值源，不回显敏感环境。

## 5. 环境与依赖

R06：以 Python 3.11 为拟定统一最低版本（现有公共代码使用 tomllib）；Git 和 jsonschema 按实际执行入口声明。实施时由导入和命令清单复核，生成可重现依赖约束，不能把主版/standalone 当前不同声明原样当成已一致。

基础安装与 doctor 不要求 Node、GUI、Docker、全部 WSL apt 包或任意 MCP。可选能力按任务探测，并报告缺失会阻塞哪一类操作。doctor 的最小诊断路径应只依赖标准库，避免依赖缺失时诊断程序本身无法启动。

Windows 与 WSL/Linux 的虚拟环境分开；不复用跨系统解释器和 site-packages。环境探测不自动安装、提权、启动 Docker、连接外部服务或修复用户环境。

## 6. 接收者流程

发布说明提供一个主入口，按以下顺序：确认支持范围及依赖 → 获取固定版本包 → 如需填写至多三项接入配置 → 安装 → doctor → 新会话示例。

安装提供预览/只读检查能力以及明确目标。具体 CLI 文件名、子命令和输出 schema 在实施计划冻结，本文不把尚不存在的命令当作可运行教程。

普通示例验证规则和方法论可见、按任务触发；GTO 示例单独验证真实无历史代理、身份绑定、独立 Review 与验收。缺少真实代理能力时普通路径可以给出其真实结果，GTO 必须阻塞，不能由主协调器冒充多个角色。

## 7. 安装所有权与不破坏约束

R07：安装器仅管理 receipt 列出的文件、目录以及明确标记的 AGENTS 管理区块。首次安装遇同名未受管技能或管理区块冲突，先停止并给出冲突清单；不以“同名”推定归属。

更新/卸载比较安装时的文件哈希。用户修改过的受管文件必须保留并报告，不能递归覆盖删除。AGENTS 非受管正文、现有 hooks、MCP、其他技能、个人记忆和其他 Codex 配置必须保持不变。现有清空 hooks 的行为必须退出默认路径。

安装目标和 staging/backup 必须处于核实边界，拒绝越界、链接跳转及大小写碰撞；receipt 损坏或缺失时不能扩大删除范围。卸载默认保留用户数据、任务证据及冲突文件，并给出残留说明。

## 8. 事务、失败与恢复

R08：生命周期操作采用 preflight → 计算变更计划 → staging → 备份受管旧版本 → 替换 → 校验 → 原子写入完成凭据的流程。同一安装范围有互斥锁；锁的属主、失效条件和崩溃恢复规则需有合同。

任意一步失败，应尝试回滚本次受管变更；完整恢复与部分恢复分别报告。磁盘不足、权限错误、进程中断和多文件替换不能假称整体原子。残留事务保留明确恢复信息，后续操作先处理该事务，不能跳过后继续宣布成功。

安装锁不等于在途任务全局锁。本版不自动迁移在途 GTO 状态；进行中的任务继续使用其冻结运行快照，版本切换只作用于适用的新任务。更新策略需避免删除仍被引用的快照或证据。

## 9. 数据与能力边界

R09：CFM 代码与记忆数据分离。分发不包含开发者的历史案例、个人索引、运行状态、凭据或本机绝对路径；数据目录需显式解析，新用户从空数据或明确人工选择的导入开始。本项目不实施个人数据同步。

能力报告分三层：文件/声明存在；当前进程可运行；真实 Codex 会话已验证。工具名称相同不代表平台权限和可见性相同。没有 node_repl 不能推断所有技能失效；GUI 不可用只阻塞依赖 GUI 的验收；子代理不可用阻塞 GTO 对应流程。

GTO 不通过修改候选控制器降低自己正在执行的门禁。本次工程以现有已安装 GTO 为治理入口，候选仅作为测试对象；控制器本身的更新要有独立校验和运行版/候选版隔离证据。

## 10. 分发与版本

R10：发布物从固定源码提交按白名单构建，清单记录版本、源提交、文件列表、逐文件哈希、依赖、构建入口及支持矩阵。相同输入应生成等价内容，并校验生成副本没有手工漂移。

源码、打包、安装、任务冻结运行版本分别可追溯。包不包含 .git、个人配置、历史任务、缓存、临时目录、凭据或作者记忆。文件哈希证明完整性，不等于发布者签名或供应链信任。

分发前核实许可、第三方材料归属与再分发条件。保留仓库原历史不等于历史已经脱敏；当前工作分支不是对外分发包，不直接推送/发布整仓历史作为产品。

## 11. 诊断与用户提示

R11：人类可读输出与结构化 JSON 对应同一结果。至少区分配置错误、路径无法核实、基础依赖缺失、可选能力缺失、未受管冲突、受管文件漂移、锁占用、路径不安全、包完整性失败、完整回滚、部分恢复、磁盘已安装但新会话未验证。

每个结果说明完成了什么、未完成什么和最小下一步。错误不触发无限重试、自动提权、自动安装或破坏性 fallback。中文路径、空格、Unicode、CRLF/LF 和有限编码控制台均进入测试范围；不因诊断编码错误掩盖原错误。

## 12. 验证层次与验收标准

R12：编写实现前冻结可重复 benchmark、fixture、唯一成功标准、证据目录及不覆盖范围。修复类分支另按 fix-closure-gate 冻结最小复现和 hit proof，结果变绿必须证明命中修复点。

| 层次 | 对象和输入 | 通过标准 | 不能替代的证据 |
| --- | --- | --- | --- |
| 静态合同 | 引用、配置/schema、依赖、生成清单 | 无活动悬空入口、无作者路径、主/分发版本一致 | 实际安装与会话加载 |
| 生命周期组件 | 临时假 home、已有 AGENTS/hooks/技能、碰撞和漂移 | 生命周期正确；不拥有文件字节不变；失败状态准确 | 真实平台差异 |
| 失败恢复 | 并发、锁、权限、磁盘、阶段中断 | 完整回滚或准确部分恢复；可安全续接 | 长期生产可靠性 |
| 平台运行 | Windows 原生、Linux、WSL 分别执行 | 路径、锁、超时树清理、编码、CLI、升级卸载通过 | 云端会话和真实代理 |
| Codex 会话 | 干净安装位置、新会话、示例 | 规则和技能实际加载，普通/GTO 模式按约定分流 | 仅磁盘文件存在 |
| GTO 流程 | 真实代理、计划/绑定/Review/验收 | 真实身份、依赖与来源回路完整，无伪造角色 | 合成 ID 或 subprocess 单元测试 |
| 干净接收者 | 无作者配置和记忆，仅发布说明与包 | 不改源码、作者人工介入 0、≤3 项配置、满足两次 CLI 主流程 | 作者熟悉环境下安装成功 |

测试、独立 Review、业务验收、干净接收者验证分别留证。角色复用与独立性按后续获批计划及 GTO 合同确定，不能临时由实现者自验替代。真实云端或新会话无法获得时，明确未验收，不以模拟测试冲抵。

## 14. 交付与推进顺序

交付一套共同真源、完整分发包、生命周期 CLI、配置/所有权/事务合同、安全安装与恢复测试、支持矩阵、接收者教程与示例、独立 Review 和各层验收证据、明确限制列表。

阶段顺序：书面规格独立审阅与用户确认 → 编制可执行计划/benchmark/角色与 DAG 并请用户确认 → 使用现有 GTO 初始化和验证六工件、冻结运行版本与能力 → 合同/测试准备 → 实现/整合 → 独立 Review 及原路返工 → 分层验收和干净接收者验证 → 最终事实同步。

计划需要明确并行写入边界、真实代理分工、串行依赖、预算、恢复路径和验收资源。父任务持续协调与最终验收；一般技术取舍在既定范围内处理。尚未书写的规格或计划不能因总体“继续实施”委托而被当成已批准。

没有作者帮助、没有源代码修改、没有隐藏全局依赖，且上述环境与会话证据满足后，才能宣称“其他 Codex 用户简单配置可用”。技术上可分发仍不等于付费意愿；后续商业验证另记录新用户完成率、节省时间、缺陷/返工变化、支持工时及愿意付费的具体服务。

- 本规则只处理“外层平台异常”和“用户目标命令失败”之间的判定边界，不替代普通命令失败闭环。
- `ghost snapshot`、`NUL` 保留名索引失败、外层 indexer / snapshot / watcher / harness 附带错误，默认先视为“平台噪音候选”，不是直接等同于“用户任务失败”，也不是直接等同于“任务成功”。

三段式判定：

- 第一段：先看用户目标命令本身是否失败。
  - 若目标命令退出码为 `0`，且核心输出、核心产物或核心副作用看起来完整，则外层 `ghost snapshot` / `NUL` 异常默认按平台噪音候选处理，不直接进入普通命令失败闭环。
  - 若目标命令退出码非 `0`，或输出已经明确显示目标命令未成功完成，则先按“目标命令失败”处理，再判断外层噪音是否只是伴随症状。

- 第二段：再看 `ghost snapshot` / `NUL` 是否来自目标命令自己。
  - 若相关错误正文就是目标命令本身输出的关键报错，且它直接导致命令非 `0`、产物缺失、路径处理失败或保留名冲突，则这不是平台噪音，而是任务失败根因，必须进入普通命令失败闭环。
  - 若相关错误只出现在外层工具、宿主、索引器、watcher、snapshot、harness 或其他附加日志里，而目标命令自身没有因此失败，则继续按平台噪音候选处理。

- 第三段：最后看产物是否完整。
  - 若目标命令表面成功，但产物缺失、内容不完整、关键验证未通过，或用户要求的副作用没有真正发生，则不能直接宣告“只是噪音”；应提升为“可疑状态”，继续做二次核对。
  - “可疑状态”默认意味着：先不要自动进入普通命令失败闭环，但也不要直接宣布任务成功；应优先补做最小验证，例如检查目标文件、目标输出、关键字段、退出码与后置断言。

执行口径：

- 只有当证据表明“目标命令本身失败”或“外层 `ghost snapshot` / `NUL` 直接影响目标产物”时，才把该异常升级为任务失败。
- 仅凭出现 `ghost snapshot`、`NUL`、reserved name、index failure 等关键词，不得自动触发普通命令失败闭环。
- 若当前证据不足以分辨“平台噪音候选”与“真实任务失败”，默认先补最小验证，再决定是否进入失败闭环；不要直接猜。
- 若最终判断为平台噪音候选，应在说明中明确写出：目标命令退出码、关键产物状态，以及为何没有升级为任务失败。
- 若最终判断为真实任务失败，应在说明中明确写出：失败证据来自目标命令本身，或该异常如何直接破坏了目标产物。

与其他规则的关系：

- Codex 正常链的命令结构仍受 `rules/items/policy/命令构造约束.md` 约束；不要为了判断噪音而回到脆弱复杂 one-liner。
- 一旦升级为真实任务失败，后续仍必须遵守 `rules/items/policy/命令失败闭环.md` 的 `record-failure -> query-before-retry -> retry -> record-success`。

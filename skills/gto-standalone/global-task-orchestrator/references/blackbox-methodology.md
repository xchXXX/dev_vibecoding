# 分层黑盒测试方法论

本页是跨 Skill、CLI、API、UI、工作流和多服务系统选择、执行与报告黑盒测试的唯一完整正文真源。其他规则、入口和测试说明只声明适用关系并引用本页，不复制层级、场景卡、结果或批准协议。具体产品的业务验收标准仍来自当前任务合同；本页决定如何用最低成本取得可信证据。

## 核心原则

对每个目标行为选择能够形成可信可观察证据的最低成本层级。黑盒不是越完整越可靠：短场景可以把候选、触发、状态和停止点固定得更清楚，也更容易判断证据究竟覆盖了什么。不同风险可以各用一个短场景，不为追求“一次跑完”重复已经取得的同候选证据。

准备状态、实际效果、业务结果和未覆盖项分别记录。机械测试、模拟、状态字段和执行者自报只能证明各自可观察的边界，不能冒充真实业务效果。CLI/API/UI 只证明实际操作过的入口；需要 UI 证据时使用真实可用的 UI 能力。

## 层级

层级描述取证深度，不表示质量等级。一个验收计划可以为不同目标行为选择不同层级。

| 层级 | 适用目标 | 最小执行边界与停止点 |
| --- | --- | --- |
| L0 准备核验 | 候选、安装、版本、环境、输入、夹具、观察与清理能力 | 不进入正式业务效果；全部准备检查形成证据即停。准备不成立记 `PREPARATION_INVALID`。 |
| L1 首次响应 | Skill 选择、Plan 首响应、CLI 帮助或 API/UI 的第一个可观察输出 | 取得首个目标输出即停，不确认后续施工，不扩展到完整流程。 |
| L2 门禁与副作用 | init、validate、阶段迁移、preflight、单次 API 写入、UI 提交门禁及其残留 | 在隔离业务根中验证一个确定性入口或相邻门禁；取得允许、拒绝和副作用证据即停，不启动无关阶段。 |
| L3 预构造状态切片 | 恢复、幂等、跨项目入口、某个中间状态的继续执行 | 复制并校验合法阶段夹具，从指定状态开始；取得该切片的输出和状态证据即停，不重放前置阶段。 |
| L4 返工或恢复路由 | Review finding、验收 finding、失败恢复、补偿动作和复验身份 | 仅在相关路由或采集器属于候选风险时，从合法路由前夹具开始；取得路由、身份和回边证据即停。未涉及该风险时不选择。 |
| L5 微型完整黑盒 | 必须跨多个阶段才能观察、且 L1-L4 组合仍不能覆盖的相关风险 | 只有下述七项简单完整黑盒条件全部满足，并有书面理由说明短场景不足时才可选择；一个冻结任务走完即停。 |
| L6 真实复杂耐久黑盒 | 多代理、网络、数据库、Docker、重 UI、多服务或其他高成本真实长链 | 默认禁用。完成准备、冻结单一场景后，必须取得绑定本次运行的用户明确批准才可开始；一次批准只允许一个场景的一次尝试。 |

GTO 这类复杂协调系统默认选 L1-L4：分别观察 Plan、门禁、状态恢复和按来源返工路由。预构造阶段夹具替代从零重复跑完整项目。只有相关跨阶段风险无法由短场景组合覆盖时，才评估 L5；不得因为“更完整看起来更放心”升级层级。

## 选择规则

主协调器逐项列出目标行为和所需证据，然后按下列顺序选择：

1. 先运行 L0，确认候选、版本、环境、输入、夹具、证据采集和清理可用。L0 不能替代效果场景。
2. 对每项风险优先选择能够直接触发并观察它的 L1、L2、L3 或 L4。多个短场景可以组合覆盖，不要求在一个会话串完。
3. 同一候选、同一目标行为已有仍有效的可信证据时不重复运行；记录引用及未失效理由。
4. 只有 L1-L4 组合无法观察相关跨阶段风险时才考虑 L5，并记录不足原因。
5. 默认选择器始终排除 L6。L6 只能由下节的当前单次批准显式加入。

简单任务做完整黑盒时，以下七项必须同时满足：

1. 不需要多个子代理。
2. 不依赖网络、数据库、Docker 或重 UI。
3. 预计运行时间短且上限明确。
4. 输入数据小、确定、可重复。
5. 已冻结明确的成本预算。
6. 完整执行比构造和维护定向夹具成本更低。
7. 不重复同一候选已经取得的等价证据。

满足七项只表示可以评估完整执行；仍须证明 L1-L4 不足，才能选择 L5。任一条件不满足就回到定向场景，或在确有复杂耐久必要时按 L6 单次批准处理。

## 场景卡

每次黑盒运行只接受一张冻结场景卡。场景卡至少包含下列字段；业务输入与评分答案分开保存，不能把预期流程、已知缺陷或修复提示放进 `business_prompt`。

| 字段 | 含义 |
| --- | --- |
| `level` | `L0` 至 `L6` 之一。 |
| `run_policy` | 运行策略：`preparation_only`、`targeted_once`、`conditional_once`、`complete_once` 或 `explicit_approval_once`。 |
| `target_behavior` | 本场景唯一主要目标行为，以及它映射的任务验收项。 |
| `initial_state` | 起始候选、业务根、版本和状态切片；使用夹具时包含夹具标识与 hash。 |
| `business_prompt` | 被测者实际收到的正常业务输入；无提示词入口时记录等价真实请求。 |
| `trigger` | 使目标行为必然或合理出现的可执行动作。 |
| `observable_evidence` | 允许采集的输出、状态、调用、文件、身份和时间等证据，以及判定所需最小集合。 |
| `forbidden_behavior` | 一旦出现就违反合同的越界、污染、错误路由或多余动作。 |
| `stop_condition` | 取得目标证据、出现禁止行为、达到预算或无法继续观察时的明确停止条件。 |
| `preparation_checks` | 开始效果观察前必须成立的版本、环境、输入、夹具、能力和隔离检查。 |
| `cost_budget` | 时间、轮次、子代理、外部调用、服务或其他适用资源的硬上限。 |
| `cleanup` | 仅针对本轮自有进程和产物的清理动作、保留证据及失败时边界。 |

达到 `stop_condition` 后立即停止该场景。不得为了积累更多截图、让结果变成通过或顺便覆盖其他需求继续执行。预算耗尽但证据不足时记 `INCONCLUSIVE`，不能自动换 ID 或添加场景重试。

runner 的最小公共预算必须含正整数 `max_seconds`、`max_attempts` 和 `max_scenarios`，布尔值不算整数。`run` 与 `probe` 必须把 `max_seconds` 传给本轮自有进程的等待入口；超时只停止该进程及其已验证进程组，并以 `cost_budget.max_seconds` 记录机械停止原因。自然语言 `stop_condition` 的业务含义仍由主协调器判断，脚本不做语义评分。

## L6 单次批准

L6 的准备和场景卡先做完，使用户批准的是一个具体、可审阅的运行。启动前必须存在当前结构化批准，且以下字段与场景和当前候选逐项完全一致：

- `task_id`
- `candidate_fingerprint`
- `formal_round`
- `scenario_id`
- `approved_by=user`
- `approved_at`

`approved_at` 记录本次明确批准的实际时间。批准只允许该 `scenario_id` 在该任务、候选和正式轮次下尝试一次；场景一旦实际启动即视为已使用，不因中断、结果无效或更换会话而恢复。宽泛实施授权、任务总体批准、其他任务或轮次的批准、历史消息和剩余预算都不能代替或推导本次批准。任一字段缺失、不一致或已使用时，runner 必须在创建本轮证据目录、临时目录、namespace 或业务进程前拒绝。

L6 的当前上下文必须指向本次任务已有的 attempt/event JSONL 证据载体。runner 先完成纯参数校验和只读重放检查，再完成候选、receipt、环境、输入、夹具与观察能力等 L0 准备；只有准备有效，才在 launcher 执行前于该文件的同一写锁内再次检查重放并原子追加 `approval_consumed` 事件。事件带批准 token、`scenario_id` 和全部绑定字段。准备失败不消费批准。新进程读取同一事件即可拒绝已经消费的批准，不另建批准数据库或第二账本。实际 CLI 的 `run`/`probe` 入口必须显式读取场景卡与当前上下文，不能从旧参数绕过统一启动门禁。

默认选择器不得返回 L6。只有主协调器先判断 L6 确有必要、准备好具体场景并取得上述批准，才把该场景交给 runner。L6 仍受 `cost_budget` 和 `stop_condition` 约束，不因获得批准变成无限耐久运行。

## 夹具与执行产物

预构造夹具保存在测试夹具真源中，运行时复制到本轮 `.tmp/` 隔离目录。runner 在使用前校验夹具清单、hash、结构，并把候选兼容标识与调用者给定的当前标识或当前 revision 合同精确核对；不使用前缀或模糊版本匹配。校验失败记 `PREPARATION_INVALID`，不得就地修改冻结夹具或带病进入效果观察。每个场景从自己的副本开始，避免前一场景污染后一场景。

原始输入、候选与安装标识、真实会话或运行 ID、公开可观察轨迹、命令退出码、产物 hash、结果分类、停止原因、成本和清理结果写入 `.artifacts/` 的本轮证据目录。评分材料留在验收侧。清理仅触及场景卡声明的本轮自有资源；失败时先保留诊断证据，不删除主工作区、其他任务、真实 CFM 数据或活动 worktree。

## 结果分类

每个场景必须且只能得到以下一种结果：

| 结果 | 判定 |
| --- | --- |
| `PASS` | 准备有效，目标行为的最小证据全部出现，且未出现禁止行为。只覆盖场景卡声明的目标。 |
| `EFFECT_FAIL` | 准备有效、触发成立，但实际行为违反目标或出现禁止行为。保留首轮事实，停止自动重跑，定位根因并向用户报告方案。 |
| `PREPARATION_INVALID` | 候选、版本、环境、输入、夹具、观察或隔离前提有证据表明不成立。先修准备并复查；不得把有效条件下的效果偏差改称准备问题。 |
| `NOT_OBSERVED` | 场景有效，但合同允许目标分支在本次触发下不出现，或条件式 L4 因候选未涉及该风险而未选。若触发本应保证目标出现，则应记 `EFFECT_FAIL`。 |
| `INCONCLUSIVE` | 证据缺失、相互矛盾、观察中断或预算先耗尽，无法可靠判为通过或效果失败。不得宣称覆盖。 |

`PREPARATION_INVALID` 的修复复查不是新的正式效果轮次，但原记录和成本保留。`EFFECT_FAIL` 不进入自动黑盒循环；普通 Review 和普通验收 finding 仍按 GTO 的来源回路闭环。`NOT_OBSERVED` 与 `INCONCLUSIVE` 都不是通过，也不能靠机械测试改写成 `PASS`。

## Memory 与 CFM 访问报告

每个真实代理场景分别报告以下四类访问，不合并成“未读记忆”：

1. `MEMORY.md` 注册表。
2. `rollout_summaries` 历史会话摘要。
3. 除前两项外的其他长期 Memory 来源。
4. CFM 的命令失败记录或存储。

每类记录 `observed_read`、`observed_not_read`、`unknown` 或 `not_applicable`，并附公开可观察证据引用。提示词写了“不读取 Memory”、使用 `fork_turns="none"` 或执行者自报未读，都不能单独证明没有访问；平台不能提供完整访问轨迹时必须记 `unknown`。报告不得读取私有推理补证据。

CFM 另列 `strict_failure_chain` 为 `true`、`false`、`unknown` 或 `not_applicable`。只有真实、非预期的命令失败链才允许按 CFM 执行 `record-failure -> query-before-retry -> record-success`；预先声明且失败类型相符的最小 TDD Red 不触发。没有真实失败时访问 CFM，或为了获取业务答案检索历史失败，均记为不严格。CFM 访问事实不推导其他 Memory 的访问事实，反之亦然。

## runner 与主协调器的边界

runner 只承担确定性工作：

- 校验场景卡字段、枚举、正整数预算和唯一 ID；一组待选场景拒绝重复 `scenario_id`。
- 执行默认层级过滤及 L6 当前批准的逐字段校验和单次消费门禁。
- 复制并校验冻结夹具的 hash、任务身份、合法阶段、工具根与业务根分离及候选兼容标识，建立本轮 `.tmp/` 与 `.artifacts/` 目录。
- 按已给定入口启动或停止本轮自有命令、进程和采集器，采集时间、退出码、标准输出、公开事件、文件与 hash。
- 将 `max_seconds` 接入本轮自有进程等待；超时停止该进程并记录机械停止原因。在 `stop_condition` 的机械条件或其他预算命中时停止，并验证结果枚举和证据清单格式。

主协调器保留语义职责：

- 从任务合同识别风险，选择能提供可信证据的最低成本层级，并说明为何不需要更高层级。
- 撰写场景卡中的业务输入、目标行为、触发、禁止行为和语义停止条件。
- 拆分场景、安排顺序与并行关系，撰写子代理提示词，完成派发、跟进和必要追问。
- 判断实际输出是否满足业务目标，给出最终结果分类、覆盖边界、根因和后续方案。
- 判断 L4 是否适用、L5 是否确实无法被短场景替代，以及是否需要为具体 L6 向用户取得单次批准。

runner 不读取自然语言需求后自行拆任务，不撰写业务提示，不选择代理，不自动扩大场景，不判断语义质量，也不在失败后自行修产品或发起下一轮。脚本提供可复现的机械护栏，主协调器对调度和质量判断负责。

## 任务级更严约束

具体任务可以在自己的控制面中声明比本方法论更严格的层级禁令、成本上限和历史证据边界。此类临时约束只维护在该任务的机器状态真源及需求与验收映射中，不回写到跨任务方法论正文，也不能放宽本页的通用门禁。

## 范围复验变更入口

现行行为与版本边界见[按验收点保留结果与范围复验](acceptance-points.md)。首次验收可分范围登记；保留任意历史轮次中仍有效的结果，最终检查完整覆盖，不要求额外整轮全绿。普通任务使用简洁清单，只有显式选择 GTO 才使用控制面。

## 恢复与登记精简

新增恢复摘要、精确工具入口、原始证据登记草稿及无文档差异的事实收尾，合同唯一见[恢复、登记与收尾](streamlined-execution.md)。现有安全门禁和旧冻结版本保持；新增入口仅适用于包含它们的运行包，实际安装以发布回执为准。

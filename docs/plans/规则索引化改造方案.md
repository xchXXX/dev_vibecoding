# 规则索引化改造方案

## 任务目标

完成本仓库规则系统索引化改造，并把项目入口、规则叶子、索引校验、子代理治理和长任务文档合同统一到可维护、可校验的结构中。

## 背景与问题

当前仓库把较多 AI 协作规则放在 `AGENTS.md` 与多份长文档中，存在以下问题：

- 规则入口与规则正文混杂，默认必读入口过重。
- 同类规则分散在不同文档中，新增和维护成本高。
- 规则缺少稳定元数据，难以做按需装配、冲突检查与自动校验。
- 复杂流程与普通规则边界不清，容易把 skill 工作流重复写入普通文档。

本次改造目标不是简单搬运文档，而是建立“项目入口最小化、规则叶子模块化、索引自动生成、冲突显式治理、测试可回归”的规则系统。

## 范围

1. 把项目根 `AGENTS.md` 收敛为默认读取入口，只保留高层硬约束与规则系统入口说明。
2. 在项目根新增 `rules/registry/` 与 `rules/items/`，把项目规则拆成独立 rule 文件。
3. 规则文件统一使用中文文件名。
4. 规则文件按 `kind` 分目录维护，作用域通过元数据表达，不通过目录编码。
5. 为规则建立统一 frontmatter schema、自动索引和校验脚本。
6. 支持“项目优先、全局补充、显式覆盖、不可静默冲突”的解析策略。
7. 同步更新仓库内相关文档与测试，保证后续新增规则可持续维护。

## 非目标

- 不把全局真源 `ai-harness` 内部结构整体搬进本仓库。
- 不在本次改造中重写 `skills/*/SKILL.md` 的核心流程语义。
- 不为 Codex 假设平台级原生 rules registry；规则解析仍由仓库文档、脚本和验证链路承载。
- 不在首版把推荐长度阈值升级为硬阻断，仅做 warning 观测。

## 约束与依赖

- 规则文件名一律使用中文。
- 项目规则与全局规则冲突时，必须通过 `overrides` 与 `override_reason` 显式声明覆盖关系。
- 可执行约束优先落到脚本、测试、doctor 或 hook，不只停留在 prose rule。
- 长任务下必须先冻结方案文档与施工文档，并在代码实施前先同步核心文档与测试。

## 方案摘要

- 用 `AGENTS.md` 承担最小入口，只保留高优先级边界和装配说明。
- 用 `rules/items/<kind>/` 收纳项目级规则叶子，并以 frontmatter 驱动索引、解析与冲突治理。
- 用 `rules/registry/*` 收纳 schema、分类规则、字段规范、索引产物与 resolved 视图。
- 用脚本与测试承接结构化校验，包括规则合同校验和长任务方案/施工文档字段校验。
- 用项目级规则把子代理等待、审阅返工路由、长任务实施顺序固化为默认必读约束。

## 设计原则

### 1. 入口最小化

- 根 `AGENTS.md` 只承担：
  - 项目边界与少量高优先级硬规则
  - 规则系统入口说明
  - 默认装配顺序说明
  - 对 skill、脚本、测试的分工说明
- 规则正文不再继续堆叠进 `AGENTS.md`

### 2. 规则叶子化

- 每条规则拆成单独 Markdown 文件。
- 每条规则只保留一个主语义分类。
- 规则正文尽量保持高密度、少重复、可引用。

### 3. 复杂流程继续归 skill

- 多步协作、编排、失败闭环等复杂工作流继续留在 `skills/*/SKILL.md`。
- 普通 rule 只负责声明何时触发对应 skill，不重复抄写 skill 全文。

### 4. 可执行约束下沉

- 可自动检查的要求优先沉淀到 `scripts/`、`tests/`、后续 hooks 或 doctor 流程。
- prose rule 主要承担入口提示、装配说明和非结构化约束，不承担唯一强校验职责。

## 规则元数据合同

每个 rule 文件统一使用 frontmatter。首版字段如下：

```md
---
id: project.policy.命令失败闭环
title: 命令失败闭环
subject: command-failure-memory
scope: project
kind: policy
priority: 100
activation: always_on
paths: []
intents: ["shell", "test", "build", "retry"]
owner: ai-governance
status: active
summary: 命令失败后先记录，重试前先查询，成功后回写。
linked_skill: command-failure-memory
enforcement: advisory
overrideable: true
override_mode: replace
overrides: []
override_reason: ""
---
```

字段说明：

- `id`：全局唯一规则标识。
- `title`：规则标题。
- `subject`：规则主题键，用于冲突识别和覆盖解析。
- `scope`：`global | project | path`。
- `kind`：`policy | workflow | architecture | quality | stack | style`。
- `priority`：同层冲突时的辅助优先级。
- `activation`：`always_on | model_decision | path | manual`。
- `paths`：`scope=path` 或 `activation=path` 时的路径匹配集合。
- `intents`：规则命中意图标签。
- `owner`：维护人或维护域。
- `status`：`active | deprecated | draft`。
- `summary`：短摘要。
- `linked_skill`：命中后优先读取的 skill 名称。
- `enforcement`：`advisory | executable_backed`。
- `overrideable`：是否允许被更小作用域规则覆盖。
- `override_mode`：首版支持 `merge | replace`。
- `overrides`：显式覆盖的 rule id 列表。
- `override_reason`：覆盖理由。

## 分类规则

规则主类固定为：

- `policy`
- `workflow`
- `architecture`
- `quality`
- `stack`
- `style`

主类判定优先级固定为：

`policy > workflow > architecture > quality > stack > style`

判定口径：

- `policy`：必须、禁止、闸门、不可绕过边界。
- `workflow`：先后顺序、处理流程、回合编排。
- `architecture`：目录边界、真源入口、层级关系。
- `quality`：测试、验证、review、验收。
- `stack`：语言、框架、工具链专属规范。
- `style`：中文输出、说明口径、表达风格。

每条 rule 只允许一个主类；跨多个主类时应拆分文件。

## 解析与装配

项目侧默认装配顺序：

1. 读取项目根 `AGENTS.md`
2. 读取项目级 `rules/registry/RULES_ENTRY.md`
3. 加载项目级 `RULES_INDEX` 中 `activation=always_on` 的规则
4. 根据任务意图命中 `intents`
5. 根据目标路径命中 `paths`
6. 若命中 `linked_skill`，再读取对应 `SKILL.md`
7. 对可执行约束，以脚本、测试与验证链路为准

全局规则参与方式：

1. 由项目级 `RULES_ENTRY.md` 显式声明引用全局规则真源
2. 解析器在当次调用中按“项目本地优先、全局按上下文补充”的方式装配规则
3. `RULES_RESOLVED.json` 输出的是按当前调用上下文解析后的生效视图，而不是脱离调用上下文恒定存在的“默认全局合并终态”

补充说明：

- 若显式传入 `-GlobalRulesRoot`，则按传入的全局规则根参与解析。
- 若未显式传入 `-GlobalRulesRoot`，是否能纳入全局规则，取决于当次脚本是否成功解析到可用的全局规则根。
- 若当次没有可用的全局规则根，则 `RULES_RESOLVED.json` 的全局部分应退化为空；这属于当前调用上下文的解析结果，不视为异常隐式兜底。

## 冲突与覆盖策略

### 基本原则

- 默认先合并，不冲突则同时生效。
- 项目规则不能静默覆盖全局规则。
- 发现冲突时必须显式声明 `overrides`。
- 被覆盖的全局规则若 `overrideable=false`，则直接校验失败。
- 冲突但未声明覆盖时，直接校验失败，不允许模糊运行。

当前实现口径补充：

- `subject`、`priority`、`override_mode` 是规则合同中的稳定元数据，但不应在文档中超前宣称所有同 `subject` 冲突都已自动检测并完成 `priority` 消歧。
- `override_mode=merge` 只有在脚本明确实现对应合并语义时，才能解读为“保留目标规则并做补充”；在未实现字段级合并前，只能把它视为合同字段和后续扩展位，不能据此假定 `RULES_RESOLVED.json` 已自动产出深度 merge 结果。

### 生效顺序

- `path` 规则可以覆盖 `project/global`
- `project` 规则可以覆盖 `global`
- `global` 不能反向覆盖项目规则
- 同层冲突若脚本已实现显式判定，则可使用 `priority` 辅助消歧；未实现自动消歧时，不应把该条解释为当前脚本已有的强保证

### 合法关系

- `merge`：保留目标规则并在其基础上补充；仅当脚本已实现对应合并语义时才成立
- `replace`：项目规则完全替换原规则
- `forbid`：通过 `overrideable=false` 阻止覆盖

## 文件与入口设计

### 根 AGENTS.md

改造后只保留：

- 中文说明口径
- 用户提问先回答
- 落盘前先给简短计划
- 命令失败闭环默认启用
- 规则系统入口与装配说明
- 真源入口与目录边界摘要
- 对 skill、脚本、测试的分工说明

### RULES_ENTRY.md

职责：

- 说明规则系统如何工作
- 说明装配顺序
- 说明冲突解析顺序
- 说明哪些场景必须转 skill
- 说明哪些校验以脚本或测试为准

### RULES_INDEX

- `RULES_INDEX.json`：机器读取索引，仅包含本地规则基础信息
- `RULES_INDEX.md`：便于人工浏览的索引视图
- `RULES_RESOLVED.json`：按当前调用上下文解析出的生效规则视图；只有在当次提供或成功解析到全局规则根时，才包含相应全局规则结果

## 风险与回退

- 若只更新 prose rule 而不补脚本与测试，后续规则容易再次漂移。
- 若在项目规则中混入全局治理全文，会重新把入口变重，破坏分层。
- 若长任务文档字段不固定，后续子代理施工与审阅会因合同缺项出现理解偏差。
- 回退策略以“保留 rules 目录结构与脚本校验”为前提；局部口径若有争议，可回退具体规则叶子或规范文档，而不回退整套入口分层。

# 任务归属、普通施工流程与工作区合同

实施状态：2026-10-20 已完成文档先行、公开入口实现、CLI 测试、独立目录分发验证、独立 review、定向安装及真实 Codex 范围验收。首审的历史覆盖/角色问题和真实模型发现的批准边界问题已分别修复并由原角色复验。逐点证据及实际模型覆盖边界见 `docs/tasks/20261020-task-workspace-governance/task.md`；安装以发布回执为准，旧 GTO 冻结包不自动更新。此结论不将 CLI 负例外推为所有未来模型行为保证。

## 适用范围与唯一真源

普通施工任务必须先调查和报告方案，批准后先同步全部受影响文档、再更新测试、再实现；实现测试通过后默认独立 review 和验收。纯问答、临时只读查看、已明确授权的普通 Git 操作不创建施工流程。正式只读审计按交付需要保存报告和证据。

普通任务的两个核心工件在 `docs/tasks/<task-id>/task.md`、`task.json`；前者是目标、范围、步骤、验收点描述和结果说明，后者是身份、绑定、生命周期及阶段证据引用。原始证据留在项目 `.artifacts/<task-id>/` 或既有证据路径。不得重复维护另一份可编辑通过列表。任务号自动生成，项目无需新增一堆配置字段。

GTO 仍以 `docs/ai/tasks/<task-id>/state.json` 及同一冻结合同为真源；不创建普通 task.json，不把普通流程再套在 GTO 外。GTO 六工件/权限/版本门禁不改变。本合同的共享目录约束适用于双方。

## 调查先于方案

调查与最小诊断按[关键前提先验证](../../../../rules/items/workflow/关键前提先验证.md)确定优先级，先验证决定后续投入是否有用的前提，再展开依赖它的文档、测试与实现；不新增生命周期阶段或记录体系。

提交可实施方案前查清已有代码、调用链、配置、工具能力和已知依赖；bug 要有最小复现、根因证据和影响范围。区分产品缺陷、项目配置、夹具准备和流程缺陷。不能把可提前完成的调查放进批准后的实施步骤。

调查可以写隔离诊断脚本、运行最小实验并留证，不能提前改正式实现。根因未查清时报告调查状态和具体缺口，不把推测写为事实。修复后的效果是验收目标，不是可预先证明的事实；施工中出现新事实仍须调查并修正范围。

方案须交代目标、范围、非目标、根因依据、步骤、代理职责、验收点及风险。小任务使用简短方案，不免除必要判断。

初始仅提出目标、缺陷或“请帮我修好”，不等于已确认调查后才提出的具体实施方案。没有可核对的既有具体方案批准时，完成必要调查和隔离留证、报告方案后，应结束本轮并等待用户明确回复；等待期间不得创建或切换实施分支、建立正式任务工件或修改交付文件。已有明确批准且当前工作仍在该方案范围内的，不重复确认。只读核对及允许的隔离诊断不受此等待限制。

## 归属决策

优先级：用户明确指定 → 父任务/交接任务号 → 当前会话活动绑定且属于追加/修复/继续 → 可核实的唯一接续记录 → 无绑定无接续的新施工目标。最后才建立任务。相似标题、同项目、分支名、干净/dirty 状态都不是归属证据。

子代理默认是父任务的执行者，不是新的顶层任务；派发携带任务入口、实际目录、分支、允许写入范围和职责，不递归启动整套流程。跨窗口交接携带原任务号。多个候选或指令冲突先只读核对，必要时问一个具体归属问题。

已完成任务的新交付通常建立新任务；旧验收被推翻时必须明确恢复原任务并保留失败记录，不自动“完成后继续”绕过身份检查。

## 普通任务生命周期

1. 调查与最小诊断 → 报告方案 → 获取或沿用已有批准。
2. 首次交付写入前建立核心工件和绑定；旧任务经用户明确归属后补登记，不能补造历史测试。
3. 同步全部受影响文档/接口/示例，标明待实现；独立测试/验收代理更新目标测试并确认预期失败。
4. 主协调器组织实现，定向测试通过并证明修复命中，完成相关回归。
5. 另一独立 reviewer 检查本次变更；修复交原 reviewer 范围复审。
6. 原测试/验收代理通过公开入口验收；验收修复交原验收者范围复验，仅影响旧审查依据时补对应 review。
7. 必需点有效通过、相关问题关闭、证据完整才完成；提交、推送、合并、部署分别报告。

主协调器、reviewer、测试/验收者使用实际平台身份；reviewer 与实现者、验收者不同，验收者与实现者不同。缺少独立代理能力则报告未完成，不能自查冒充。测试与验收同一责任人延续，返工不每次新派角色。共享工作区由主协调器统一 Git 操作；两个代理涉及同文件、锁文件或共享生成物优先串行。review/验收针对固定的改动快照，相关写入需停止。

纯文档变更使用适用的一致性/链接/示例检查，不编造 TDD Red。已通过点按实际影响保留；登记错误不重跑业务。程序检查形式与身份引用，不能仅凭填写字段证明真正研究、审查、授权或验收，须交叉核对原始事件。

## 工作区分配与交接

默认每项活动任务一个主目录、一条任务分支。优先已绑定目录 → 可安全使用的当前目录 → 已有空闲适用目录 → 必要的新目录。原始主目录可以施工，无须永久空置在 main。

- own dirty：继续原目录，不自动 stash、搬动或另建。
- clean occupied：仍不能接管、切分支。
- unknown/mixed dirty：先确认归属，不一起提交。
- 绑定失效、目录缺失、分支不符：恢复处理，不静默创建替代目录或复制 GTO 状态。
- 独立任务并行写入：不同目录和分支；同任务子代理默认共享。确需独立版本实验时主协调器记录例外及合并边界。
- 一个任务同一时刻只有一个写入协调者；交接先停止/收回全部原写入安排，再转交，旧窗口默认只读。不能靠改一个字段假设旧进程已经停止。
- 端口、数据库、全局安装不受 worktree 隔离；分别核对实际占用。

本地定位索引保存在 Git common dir 的 `ai-harness/task-bindings.json`，仅保存 task_id 到工作区、模式、相对任务入口的映射。任务记录是真源；索引不能保存另一份任务状态或独立过期时间。更新使用短暂原子目录锁 `task-bindings.lock`；冲突返回阻塞，残留锁须核实进程后恢复，不按心跳/时间自动回收。不同 clone 不自动扫描/绑定；Windows/WSL 同 checkout 要通过已核实的同一 WSL Git 路径调用。

只读 inspect 不创建目录/索引。缺索引时只发现当前 Git worktree 列表中可访问目录的标准任务入口；不扫描其他仓库，不读取凭据。已有 GTO/普通任务可作为占用证据。损坏或不可访问的已登记记录不能解释为空闲。原子锁内重新发现、核验再登记，避免双窗口同时认领。

## CLI

入口 `python3 scripts/task_workspace.py --repo-root PATH --action ACTION --json`，项目副本为 `modules/tooling/task_workspace.py`。只操作记录，不创建、切换、移动、删除 worktree，不提交/推送。

通用 `--task-id ID`、`--coordinator PLATFORM_ID`；任务号只允许字母数字、连字符、下划线。项目 Git 策略沿用 `config/ai/git-policy.json`。任务字段/本地索引损坏返回 exit 2，归属冲突、门禁缺失返回 exit 1，成功 exit 0；错误只返回机器码和安全说明，不输出凭据。

| action | 输入与效果 |
|---|---|
| inspect | 可选 task-id；只读返回 `decision`（`reuse`、`available`、`occupied`、`unowned_changes`、`blocked`）、绑定和错误。无绑定不等于授权创建 |
| begin | coordinator 必填；可选 task-id（否则自动生成）、`--title`、重复 `--point ID`（默认 delivery）。当前目录必须空闲、无未知 dirty，且已在合规任务分支。写两个核心文件及定位索引；不创建分支 |
| adopt | task-id、coordinator、`--basis` 必填；用户明确确认旧任务归属后补登记或采用已存在的手工普通工件。记录原分支及 HEAD；不覆盖其他活动归属，不认领 GTO，不凭此为未来新任务豁免命名 |
| resume | 定位同 task-id，返回实际目录；同协调者续接，异协调者返回 `HANDOFF_REQUIRED`。不修改目录或状态 |
| check | 当前目录必须正好匹配绑定、分支及协调者；dirty 本身不失败。子代理使用父协调者绑定并携带实际派发记录，不能借此取得 Git/协调权 |
| handoff | 原 coordinator、`--next-coordinator`、`--writes-stopped`、`--basis` 必填；同目录转交记录。停写声明需由主协调器与实际代理状态核实 |
| record-stage | coordinator、`--stage`、`--evidence`（项目相对 JSON 路径）必填；按下述证据合同追加引用，不覆盖旧记录 |
| complete | 核对阶段证据和全部必需点、独立身份、未关闭问题；只完成任务记录，不删除分支、目录或证据 |
| register-gto | task-id 必填；从原 GTO state 检查 task_id、checkout_binding、workspace 分支。只登记定位引用，不写 state，不为 GTO 创建普通工件；GTO阶段/恢复仍调用其冻结入口 |

普通 task.json 最小字段为 schema_version=1、mode=ordinary、task_id、status、phase、branch、workspace=`<repo-root>`、coordinator、task_document、acceptance_points（仅点 ID）、stages（阶段证据引用，默认空）。登记后补充 checkout_binding（实际 checkout 路径的摘要，不是明文机器路径），阻止复制活动记录冒充原目录。本地索引保存绝对工作区定位；通用配置和示例不固定机器路径。旧手工记录可通过 adopt 补充默认字段，不丢已有字段。可移植指工具/新消费项目可独立运行，不代表已有活动状态可以无手续搬迁。

阶段顺序 `investigation → plan → documentation → tests → implementation → review → acceptance`。证据 JSON 包含 `actor`（真实平台身份）、`outcome`（pass/fail）、`summary`、`evidence`（非空相对原始文件路径列表）；tests 另有 `red_observed` 或非代码适用说明 `not_applicable`；review/acceptance 另有 `dispatch_evidence`（真实派发原始记录路径）；acceptance 另有 `checks`（id/status/evidence）与 `open_issues`。每次登记保存文件哈希并验证引用存在、限于项目；不运行业务或模型。调查/方案可引用本任务批准前已有原始证据，禁止制造过去的时间或执行证明。

完整覆盖由最后一份验收覆盖报告负责：可以引用任意历史仍有效结果，但必须明确本次实际改动影响、采用来源和未关闭问题，不靠时间或版本号全部失效。record-stage 保存所有失败，后续阶段不能跳过前置阶段最后一次真实失败；复验同阶段不强制重新登记无关阶段。是否需要补 review 由原 reviewer/验收者判断并在原始报告记录，工具不声称能从自由文本自动证明范围有效。complete 核对每点最后结论，缺失/未执行/证据不全/同点后续失败均不通过。

新增任何阶段登记后，最后完整覆盖报告必须在它之后；旧报告保留但不能直接据此完成。补一份明确采用历史有效结果的新覆盖报告即可，不要求整轮重跑或全面 review。测试者/reviewer 取阶段历史首次真实登记身份，后续不得无授权换人；实现身份取全部历史集合，历史实现者不能在换协调者后成为独立 reviewer/验收者，原 reviewer/测试者也不能倒转为实现者。本次不增加角色更换入口，确需更换应报告缺口，不能以新身份清掉原责任。

## 分支、版本与分发

项目前缀可以是 `codex/feat-` 等合法 Git 前缀，不强制结尾 `/`。新建检查遵从当前策略；仅通过真实任务绑定恢复的旧分支允许继续，不能增加永远接受所有 `codex/` 的豁免。可选 Git checker `--task-id ID --coordinator ID` 只对有效普通绑定、实际分支相同的旧任务应用命名例外；其他规则不跳过。无绑定的旧 Git 检查调用继续严格按策略。

`sync_git_workflow.py` 从 scripts 真源生成并列检查器与任务入口；`bootstrap-local.py --git-workflow-only` 定向发布这两者、全局模板及相关回执，不改其他技能/插件/冻结包。该模式名称沿用，范围增加须在回执列明。GTO 文档更新进入新生成包，旧固定运行包不替换。新会话实际加载、磁盘安装、行为验收分别报告。

规则文本与工具检查不能拦截任意文件工具/自由 shell。必须通过真实 Codex 事件核对执行顺序、派发身份、创建次数和写入范围；最终目录数量相同不代表没有先建后删。验收场景唯一见本次任务工件，测试提示不告知期望工作区数量。

# Benchmark 设计

当 benchmark 结构还不清楚、你需要解释某个套件为什么属于诊断还是验收，或 fixture 已经开始产生假信号时，阅读本说明。

## 默认分层模型

默认从以下层开始，只有在有明确理由时才调整：

- `contract`：验证 metadata、文档、prompt、schema 或说明文本是否表达了正确行为与触发语义
- `component`：验证核心脚本、函数、helper、parser、scorer 或状态机在隔离环境下是否正确
- `forward`：带着可见 setup 和明确编排，真实跑一遍端到端链路
- `blind`：隐藏实现提示，在更接近真实使用的条件下看系统是否还能自己做对

不是每个问题都必须用到所有层，但跳过某层必须是有意识的决定。

## 每层只问一个问题

每层只回答一个问题。好的问题示例：

- `contract`："description 是否表达了正确触发语义？"
- `component`："matcher 面对这个输入时，是否返回正确的 case id？"
- `forward`："完整链路从 setup 到结束，是否产出了预期 artifact？"
- `blind`："不给提示时，agent 是否会自主采取预期动作？"

反例：

- “新设计看起来合理吗，runtime 能跑吗，模型会自动触发吗？”

这其实是三个问题，必须拆开。

## 稳定 Fixture 规则

把 fixture 质量视为 benchmark 本身的一部分：

- 优先使用确定性的本地输入，而不是远端依赖。
- 每个 case 都要有唯一标识和唯一 PASS 标记。
- setup 成本要足够低，保证迭代过程中能反复重跑。
- 失败原因要编码得足够清楚，保证 case 挂了之后仍然有诊断价值。
- 除非 benchmark 本来就在测状态延续，否则要避免隐藏状态污染后续运行。

## 诊断与验收的区别

如果一个套件的主要作用是定位失败发生在哪个阶段，它就是 `diagnostic benchmark`。

如果一个套件决定这次改动是否可以交付、合并或放行，它就是 `acceptance benchmark`。

常见模式：

- 便宜、确定性强的套件作为诊断基线
- 一到两个更贴近真实使用的套件作为最终验收

不要让一个脆弱的诊断 harness 去阻断一个已经通过真实验收 benchmark 的改动。

## 输出检查单

在开始实现前，这套 benchmark 包至少要回答：

- 这次 benchmark 保护的用户可见结果是什么？
- 为什么存在这些层，而不是别的层？
- 每一层的唯一通过条件是什么？
- 哪些 fixtures 是复用的、要新建的、还缺失的？
- 哪些套件只是诊断用？
- 哪些套件构成最终验收闸门？
- 每次运行后必须保存哪些证据？

## 常见反模式

- 只写“补测试”，却没有通过阈值
- 所有层都使用同一套含糊的成功描述
- 改动本身和网络无关，却把 suite 建在公网随机性上
- 把“编排方便”误当成“评估有效”
- 在号称 blind run 的情况下让模型看到了隐藏答案

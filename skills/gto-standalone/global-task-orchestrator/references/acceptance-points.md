# 按验收点保留结果与范围复验

状态：程序实现、独立 review 与独立验收已完成；适用于本次生成版本。本文是通用原则与本次字段变更的唯一正文；旧冻结运行版本继续遵循其自身合同，不原地升级历史任务。

## 普通任务与 GTO 共用原则

普通任务使用“验收点、关联范围、结果、原始证据、来源轮次、失效原因”清单即可，无须创建 GTO 控制面。GTO 使用现有 state、attempt 和证据文件实现同一原则，不增加服务或数据库。

每个点分别记录 pass、fail、not_run、blocked。失败只影响该点和实际依赖范围，不能吞掉同轮其他通过项。最终检查全部必需点当前有效通过、相关问题关闭、证据完整；不要求某一轮全绿，也不触发额外执行。

有效结果可来自任意历史轮次。由新到旧检查真实执行记录：后来失败是阻挡旧通过的屏障；未执行不能充当通过，也不能清除已有真实失败。证据缺失、改写、输入或判定条件不一致不能算有效通过。查询、登记、格式修正和覆盖计算均不调用业务入口。

观察先后由原始运行证据决定；重新登记或准备观察的正式采用不产生新观察。新运行使用 [运行证据](runtime-evidence.md) 的完成前驱摘要表达因果顺序，单调时钟仅证明本次耗时，墙钟仅作原始诊断。不存在可靠先后关系时保守保留失败，不能靠墙钟大小或登记先后覆盖失败。

环境重试额度限制自动续跑，超过额度仍可按每次明确的用户授权继续本次范围，见[控制器指南](controller-guide.md)。已通过点继续保留，授权后的真实失败也完整登记，不通过清空失败、换候选或重测无关通过点恢复流程。

关联范围通过已有 acceptance_items.paths 声明，包含该点逻辑、公共依赖、输入夹具和判定脚本。新增可选 depends_on 引用其他验收点，传递展开；缺省为空。entry 可选声明真实执行入口，capabilities 显式空数组表示该点无需额外能力；省略时继承现有模板能力声明，模板也未声明时为空。没有 paths 的点保守依赖已声明候选的全部功能输入。无关文件、文档和版本标识变化不自动使所有点失效；不能把真正参与判定的配置版本当成无关元数据。

每个结果绑定执行时的关联范围及文件内容摘要、验收点定义和原始证据摘要。内容未变时直接采用，不增加 review。内容改变默认使命中点及其依赖失效；同文件无关修改等需要语义判断时，由原验收者或原发现者提交范围判断，绑定实际完整差异和具体来源，不另派全面 reviewer。

普通、模型、页面检查可以独立安排和登记，不预设项目必须包含任何一种能力。一个范围 pending、失败或工具不可达不妨碍其他范围完成。能力证明针对实际绑定执行者；缺失能力只阻塞依赖它的点，不删除历史通过记录。

效果失败的停止和下一轮授权只约束失败点及依赖它的范围；独立点可首次安排和登记，其成功也不能解除另一点的停止。

准备阶段只检查输入、夹具、机械测试、证据采集、登记格式和确实需要的运行前提。实际完成且满足正式结果合同的测试可直接正式登记；可访问、已启动、版本一致等准备事实不等于功能通过。昂贵场景启动前先排除上述低成本问题。

失败时先保存输入、输出、事件、实际执行次数和成本，再清理自有资源。编号、格式、解析或登记失败只修正记录；原始结果足够时重新整理提交，不重新执行业务。原始失败不可覆写为成功。

未绑定且未执行的错误安排可以留痕撤回；已经绑定而无法证明未执行的安排不得撤回。已执行者必须保存结果与成本。撤回不清除历史编号、不伪造成功、不消耗实际运行预算。

## 状态与公开入口合同

继续使用 create-subtask-attempt、bind-dispatch、validate-result、record-subtask-result、finalize-task。新增 acceptance-status 只读报告当前逐点覆盖、来源 attempt、状态及失效原因；withdraw-subtask-attempt 只撤回未绑定、无结果的安排，载荷为 written_by、written_role=coordinator、reason。

create-subtask-attempt 可用 --result-json-file 提交 {"scope_acceptance_ids":["CHECK-01"]}；省略时选择对应 kind 当前缺失、失败或失效的点。无需重写完整合同或填写保留项。普通与 blackbox 沿用现有 kind；模型与页面以各自模板和验收点范围区分，不内置业务名称。

expensive_acceptance 新增 point_results 数组，每项为 {acceptance_id,status,evidence_refs}；pass/fail 必须有真实原始证据，not_run/blocked 可另给 reason。scope_acceptance_ids 覆盖本次安排，缺失项明确视为未执行。evidence_by_acceptance_id 只存本次实际通过项，不把保留项复制成新执行；控制器保存逐点定义、依赖内容和证据哈希，不让调用者伪造摘要。

整体 outcome 仍如实表示本次运行：混合失败保持失败，部分成功可使用 partial_pass；它不再代表全局覆盖。partial_pass 不要求额外批次 review。所有结果沿用既有 writer、run_evidence、usage_evidence、真实调用次数及失败证据检查。准备事实不进入 point_results；准备中完成的正式测试应作为对应普通范围登记并引用原始运行，不重跑。

acceptance-status 返回 `{ok:true,complete:boolean,points:{ID:{status,source_attempt_id?,reason}},rerun_acceptance_ids:[ID]}`，从全部历史逐点结果计算覆盖，不修改历史。状态为 pass、fail、not_run、blocked、missing、invalid。点定义或相关内容变化返回 invalid，并说明原因。较新 fail 优先于较旧 pass；同轮 pass 不因同轮其他点失败失效。最终文档和 finalize 使用同一覆盖计算，仍保留独立 review、finding 和必需证据门禁。

现有 record-acceptance-evidence-batch/record-acceptance-coverage 继续负责有多个单元的原始证据归档；内容相同的复用不再强制 applicability_review。旧轮次真实性、来源、哈希、单元集合和真实评分检查保留，语义影响判断仍回到原发现者或验收者。

批次按每个验收点所需的完整单元集合投影，可以与其他轮次的逐点结果合并。一个点的关联内容、采用单元或失败屏障变化不连带作废其他点。登记时核验整份运行；后续消费核验原 manifest 绑定、公共输出和实际采用的文件。未采用的历史辅助记录损坏列为 `evidence_warnings`，保留原回执并修复归档，不阻断已完整有效的覆盖，也不触发业务重跑。

混合失败来源中独立证明通过的单元，不受该来源自身的聚合失败阻挡；缺少必需单元仍不能通过，其他后来真实失败仍构成屏障。历史结构校验保留冻结合同、夹具和身份约束，但不读取未采用批次的可选范围判断及附件；实际采用时仍完整核验这些证明。该交叉边界已通过定向复验。

## 最小示例和版本边界

范围判断公开入口：`record-acceptance-impact` 接收 `written_by/written_role/source_attempt_id/point_ids/changed_paths/reason/evidence_refs`，由原验收者或原发现者判断同文件等改动未影响指定点。控制器绑定源 attempt、完整实际差异、当前点定义及证据摘要；不允许隐藏改动、外来身份或以范围判断抹除后来失败。

准备中已完成的正式测试可由普通结果的 `source_preparation_attempt_id` 引用。同候选、同执行者、原始 run manifest 和逐点输入输出必须匹配；采用动作 `real_call_count=0`，原准备保留实际成本。原始记录至少可识别 `acceptance_id/status/input/actual/expected`，准备事实日志不能冒充这种正式观察。该分支只重新登记证据，不执行检查入口。

示例使用十个通用 CHECK 编号及相对路径。首次执行十点，九点通过一点失败；修复改动只命中两点，下一安排自动选择这两点。执行计数必须为 10 + 2，另外八点保留原始 attempt；完成只检查覆盖，不执行第三轮。

复制示例后仅替换检查入口、关联路径和实际需要的能力。独立分发从真源通过既有生成、打包入口刷新，禁止手工维护第二套控制器。验收在独立临时目录中运行解压包，隔离原 harness 和业务项目路径，并验证相对路径与执行次数。

全局安装更新只影响新任务入口，不改写已有冻结 runtime_snapshot。旧任务使用其记录的快照和合同；未冻结旧任务升级须显式处理版本边界，不能静默改写历史证据。本次已验证独立包与冻结版本边界；全局安装仍由既有安装流程显式更新。

## 恢复与登记精简

新增恢复摘要、精确工具入口、原始证据登记草稿及无文档差异的事实收尾，合同唯一见[恢复、登记与收尾](streamlined-execution.md)。现有安全门禁和旧冻结版本保持；新增入口仅适用于包含它们的运行包，实际安装以发布回执为准。

任务身份与目录接续：同 task_id 的 Plan/Execute、子代理和复验沿用已绑定工作区、分支与冻结包；不同会话不自动成为新任务，dirty 不触发新建。共享目录的冲突写入串行、Git 由主协调器统一，交接先停止原写入。普通任务核心工件与流程另见 harness 的 docs/modules/git-workflow/contract/task-workspace.md，不叠加到本 GTO 合同。新定位入口不改写 state 或绕过 checkout_binding；相关新增能力仍以安装版本及验收记录为准。

本文基于 LangChain 官方文档中 LangGraph 的 Graph API 总览页整理，目标不是逐句硬翻，而是把原文改写成更适合系统学习的中文讲解稿。

原始页面：
- [Graph API overview - LangChain Docs](https://docs.langchain.com/oss/python/langgraph/graph-api)

## 1. 先建立整体脑图

LangGraph 可以把一个 agent 或工作流理解成一张“会流动的图”。

这张图里最核心的只有 3 个概念：

- `State`：共享状态。它代表应用在当前时刻的“全量上下文快照”。
- `Nodes`：节点。每个节点就是一段逻辑，会读取当前状态，做计算或副作用，然后返回状态更新。
- `Edges`：边。它决定下一个该跑哪个节点，可以是固定跳转，也可以是条件分支。

可以把它理解成：

1. 当前状态先进入某个节点
2. 节点执行后产生一部分状态更新
3. 图根据边的规则决定接下来去哪里
4. 不断重复，直到走到 `END`

如果你以前写过 agent loop，其实 LangGraph 做的事就是把“状态 + 决策 + 执行流转”显式结构化。

---

## 2. Graphs 是什么

Graph 就是把节点和边组织起来的执行图。

官方文档里主要讲的是 `StateGraph`。它适合绝大多数基于共享状态的 agent 场景。

### 2.1 `StateGraph`

`StateGraph` 是最常用的图类型。它的核心思想是：

- 整张图共享一个状态对象
- 每个节点读取这个状态
- 每个节点只需要返回“自己要更新的部分”
- LangGraph 负责把这些更新合并回总状态

这意味着你不需要手工把所有上下文在线程之间来回传递，图本身会帮你维护状态演化。

### 2.2 编译图

图定义好以后，需要调用 `.compile()` 才能得到真正可运行的 graph。

编译阶段通常也会把这些能力接进去：

- `checkpointer`：做断点恢复、线程持久化
- `cache`：做节点缓存
- 其他运行期能力

可以把 `compile()` 理解成“把图的声明式定义，变成一个真正能执行的运行体”。

## 3. State：LangGraph 的核心

如果只记住一个概念，那就是 `State`。

LangGraph 的很多设计都围绕它展开。

### 3.1 State 是什么

`State` 是全图共享的数据结构。它可以是多种 Python 类型，但实践里最常见的是：

- `TypedDict`
- `dataclass`
- `Pydantic BaseModel`

通常推荐先从 `TypedDict` 开始，因为最直接。

### 3.2 Schema：状态结构怎么定义

状态 schema 的意义是告诉图：

- 状态里有哪些字段
- 各字段是什么类型
- 节点会读写哪些字段

一个常见误解是：节点只能写自己输入 schema 里出现的字段。

不是。

更准确地说：

- 节点函数参数里声明的 schema，只决定“这个节点以什么视角读取状态”
- 但节点返回时，可以更新图里已知的任意状态通道

也就是说，图的总状态可以大于某个节点看到的局部状态。

### 3.3 多种 schema 并存

这是 LangGraph 很重要的一点。

一个图里可以同时存在多种状态 schema：

- 输入 schema：图接收用户输入时暴露什么
- 输出 schema：图最终对外返回什么
- 总状态 schema：整个图内部完整状态
- 私有 schema：某些内部节点使用、但不想对外暴露的字段

这样做有两个实际好处：

1. 内部节点可以传递中间信息，不污染对外接口
2. 图的输入和输出可以保持极简，但内部实现仍然足够丰富

你可以把它理解为：

- 对外接口是“收口”的
- 内部流转是“展开”的

### 3.4 Reducer：状态更新怎么合并

多个节点写同一个 state key 时，LangGraph 需要知道“怎么合并”。

这就是 `Reducer` 的作用。

Reducer 本质上是在说：

- 新值来了以后，是覆盖旧值？
- 还是和旧值拼接？
- 还是做自定义合并？

### 3.5 默认 reducer

默认情况下，多数字段采用“覆盖”语义。

也就是：

- 节点返回了某个 key
- 这个 key 的新值会替换旧值

这适合标量字段，比如：

- `status`
- `final_answer`
- `selected_tool`

### 3.6 列表字段常见写法

如果你希望列表不断追加，而不是每次覆盖，就要显式声明 reducer。

常见方式是使用 `Annotated[..., add]`。

比如一个 `list[str]`：

- 默认行为可能是整个列表被新值替换
- 加了 `add` 之后，多个节点返回的列表会按追加方式合并

这一点非常关键。很多初学者状态丢失，往往就是 reducer 没配对。

### 3.7 Overwrite 语义要慎用

覆盖更新本身没错，但你要清楚：

- 覆盖适合“唯一真值”
- 追加适合“累积历史”

如果是消息记录、步骤轨迹、候选结果集合，通常不该直接覆盖。

## 4. 在状态里处理 messages

LangGraph 对消息有专门支持，因为 agent 场景里最常见的数据就是对话消息。

### 4.1 为什么要用 messages

把消息放进 graph state，有几个直接收益：

- 对话上下文天然成为图的一部分
- 节点可以持续读写对话历史
- 工具调用、人工中断、恢复执行时更自然
- 和 LangChain 的消息对象体系能更好对齐

### 4.2 消息既支持对象，也支持字典

文档明确说明：

- 可以传 `HumanMessage` 这类消息对象
- 也可以传 `{"type": "human", "content": "..."}` 这种字典形式

这让消息输入更灵活，也更容易和前端、存储层、API 层对接。

### 4.3 `add_messages`

如果你的状态里有 `messages` 字段，通常要给它配 `add_messages` reducer。

原因很简单：

- 消息不是普通列表追加那么简单
- LangGraph 需要按消息语义做合并
- 某些情况下还会处理消息 ID、序列化与恢复

所以：

- 普通列表累积，用 `add`
- 消息列表累积，用 `add_messages`

不要混用。

### 4.4 `MessagesState`

如果你的图本来就是对话型 agent，可以直接继承 `MessagesState`。

它相当于给你预先准备好一个常用的状态基类，至少包含消息字段及其合适的处理方式。

如果你还需要额外字段，比如：

- `documents`
- `tool_results`
- `plan`

可以在 `MessagesState` 基础上继续扩展。

### 4.5 Serialization：消息序列化

消息在图里流转、持久化、恢复时，会涉及序列化。

你真正要记的是：

- 尽量使用 LangChain/LangGraph 认可的消息结构
- 不要自造和官方消息体系完全不兼容的格式

否则断点恢复、持久化、追踪时容易出问题。

## 5. Nodes：节点怎么理解

节点就是图里的执行单元。

一个节点通常做三件事：

1. 读取当前状态
2. 执行逻辑或副作用
3. 返回状态更新

### 5.1 节点能接收什么参数

文档里提到，节点除了能接收 `state`，还可能接收：

- `config`：运行配置，如 `thread_id`、trace tags 等
- `runtime`：运行期对象，里面可以拿到 `context`、`store`、`stream_writer`、执行信息等

这说明节点不只是纯函数，它也可以获得运行时环境。

### 5.2 节点命名

添加节点时可以显式命名，也可以基于函数名命名。

工程实践上建议：

- 名称要稳定
- 名称要表达职责
- 不要频繁改节点名

原因是节点名会影响：

- 路由逻辑
- 调试
- 可视化
- 线程恢复和迁移

### 5.3 重新执行与幂等性

这是文档里很重要但容易被忽视的一点。

某些情况下节点可能被重新执行，例如：

- 从 checkpoint 恢复
- 重试
- 中断后继续

所以节点最好尽量具备幂等性。

也就是：

- 同样输入重复执行，不要产生不可控副作用

尤其是这些操作要格外小心：

- 调外部 API
- 扣费
- 发邮件
- 写数据库
- 调工具造成真实世界变更

### 5.4 在节点里使用 task

官方建议：如果节点里包含可能需要 checkpoint 的副作用或子任务，可以把它们包装成 `task`。

这样做的核心价值是：

- 子任务可以被更好地追踪
- 在恢复执行时，避免重复做同一个昂贵或有副作用的动作
- 更适合并发发起多个独立操作

简单说：

- 普通节点适合组织流程
- `task` 适合承载“可单独恢复/等待/收集结果”的子执行单元

### 5.5 `START` 和 `END`

LangGraph 提供两个特殊节点：

- `START`：图入口
- `END`：图结束

它们不是你自己实现的业务节点，而是图结构里的边界标记。

你通常会写：

- `START -> 某个起始节点`
- `某个终止节点 -> END`

### 5.6 Node caching

LangGraph 支持节点缓存。

缓存的意义是：

- 相同输入再次进入同一节点时，可以直接复用结果
- 避免重复做昂贵计算

缓存一般要关注两个点：

- `key_func`：如何生成缓存 key
- `ttl`：缓存多久过期

适合缓存的节点通常是：

- 纯计算
- 昂贵但稳定的推理步骤
- 输入相同则结果基本相同的处理

不适合缓存的节点通常是：

- 强依赖当前外部环境
- 每次都要取最新数据
- 含强副作用

## 6. Edges：边决定执行流

边就是“下一步去哪”的规则。

### 6.1 Normal edges

普通边最简单，就是固定跳转。

比如：

- `node_a -> node_b`

意思是 `node_a` 执行完，下一步必然去 `node_b`。

### 6.2 Conditional edges

条件边会调用一个路由函数，根据当前状态决定下一步走向。

这是构建 agent 分支、工作流判断、失败回退的核心手段。

常见用法有两类：

1. 路由函数直接返回下一个节点名
2. 路由函数返回某个值，再通过映射表映射到节点

适合场景：

- 是否继续推理
- 是否调用工具
- 成功 / 失败分流
- 人审 / 自动执行分流

### 6.3 Entry point

入口点本质上就是：

- 用户输入来了以后，先从哪个节点开始执行

最常见写法是从 `START` 指向某个固定节点。

### 6.4 Conditional entry point

如果图一开始就要根据输入动态分流，可以让 `START` 也走条件边。

这很适合：

- 不同任务类型进入不同子流程
- 根据输入特征挑选不同 agent

## 7. `Send`：做动态分发

`Send` 用于把一份状态“拆成多份目标输入”，动态发往一个或多个节点。

它特别适合 map-reduce 风格的场景。

例如：

- 状态里有多个 `subjects`
- 你希望对每个 `subject` 都跑一次 `generate_joke`

这时可以返回一组 `Send(...)`，相当于：

- 给每个目标各发一份定制输入
- 让图动态展开并行或批量处理

直觉上可以把 `Send` 理解成：

- 不是只决定“下一步去哪里”
- 而是决定“把哪些定制任务发给哪些节点”

它比普通条件边更适合“一对多展开”。

---

## 8. `Command`：把“更新状态”和“控制流”合并到一起

`Command` 是 Graph API 里非常关键的高级能力。

它允许你在一次返回里同时表达：

- `update`：我要更新哪些状态
- `goto`：我要跳到哪个节点
- `graph`：我要不要跳到父图
- `resume`：我要不要继续一个被中断的流程

简单说，`Command` 就是“带控制意图的返回值”。

### 8.1 从节点返回 `Command`

普通节点返回的是字典，表示状态更新。

如果你想让节点自己决定下一步去哪，就可以返回 `Command`。

这适合：

- 节点内已经做完决策
- 不想再额外拆一个条件边函数
- 想把“更新状态 + 跳转”放在同一个地方维护

### 8.2 `update + goto`

这是最常见用法。

例如一个节点可以：

- 先把 `foo` 更新成新值
- 再立即跳到 `my_other_node`

它的价值在于把“结果”和“控制流”绑定在一起，减少分散逻辑。

### 8.3 `graph = Command.PARENT`

如果你在子图中执行，而下一步想切回父图，可以在 `Command` 里指定目标图为父图。

这类能力对多层图、子图嵌套场景很有用。

### 8.4 `resume`

`resume` 用于在执行被 `interrupt()` 暂停后继续图。

这通常出现在：

- 人工审批
- 用户补充输入
- 外部确认

官方文档特别强调了一个容易踩坑的点：

如果你只是想给图一个新的普通输入，不要误用 `Command(update=...)`。

因为：

- `Command(resume=...)` 是“从上次中断点继续”
- 普通字典输入是“从图入口重新开始一轮”

这两者语义完全不同。

### 8.5 从工具返回 `Command`

不只是节点，工具内部也可以返回类似的控制结构。

这意味着：

- 工具不只是生产数据
- 它也能影响后续执行流

这对复杂 agent 很有用，但同时也意味着控制流会更隐蔽，使用时要保持克制。

## 9. Graph migrations：图变更后的兼容性

当图已经有历史线程、checkpoint、运行中的会话时，修改图结构就不是纯本地重构了。

官方文档给出的迁移原则可以简化为下面几条。

### 9.1 已结束线程

如果一个线程已经执行到图末尾、没有停在中断点，那么图拓扑基本都可以改：

- 增加节点
- 删除节点
- 改边
- 重命名节点

### 9.2 已中断线程

如果线程正停在中断状态，拓扑改动会受限。

文档特别指出：

- 这时一般支持多数拓扑变更
- 但重命名或删除节点会有风险

原因很直接：

- 那个线程可能下一步正准备进入某个旧节点
- 你把它删了或改名了，它就找不到了

### 9.3 State key 的变更

状态字段层面，兼容性大致是：

- 新增 key：通常兼容
- 删除 key：通常也能处理
- 重命名 key：旧线程里保存的旧状态不会自动迁移成新字段
- 改类型且不兼容：旧线程可能出问题

所以生产里更稳妥的做法是：

- 优先新增字段
- 延后删除字段
- 少做直接重命名
- 类型变更尽量做阶段性迁移

## 10. Runtime context：把运行期上下文注入图

图不仅能接收业务输入，还能接收运行时上下文。

例如：

- 当前用户是谁
- 选用哪个模型供应商
- 当前环境是测试还是生产

### 10.1 `context_schema`

可以在建图时定义 `context_schema`，明确上下文结构。

例如可以定义：

- `llm_provider`
- `user_id`
- `tenant_id`

这样节点里通过 `runtime.context` 读取时会更清晰。

### 10.2 为什么 context 不直接塞进 state

因为两者角色不同：

- `state`：是图执行过程中不断演化的数据
- `context`：更像这次运行的环境参数

把所有东西都塞进 state 会让语义变乱。

一个简单判断标准：

- 会被节点逐步更新的，用 `state`
- 是这轮运行的背景条件的，用 `context`

## 11. Recursion limit：防止图无限循环

图如果存在回路，就可能跑不出来。

LangGraph 提供 `recursion_limit` 来限制最多执行多少步。

这不是传统递归函数的概念，而更像：

- 整张图本次执行允许走多少次节点跳转

### 11.1 为什么需要它

典型场景：

- agent 一直在“思考 -> 路由 -> 再思考”
- 条件判断有 bug
- LLM 决策迟迟不收敛

这时没有上限就可能无限循环。

### 11.2 两种处理思路

文档里体现了两类思路。

第一类是被动式：

- 让图超限后抛出异常
- 统一在外层捕获，比如 `GraphRecursionError`

优点：

- 实现简单

缺点：

- 用户体验一般
- 图内部拿不到一个优雅收尾机会

第二类是主动式，官方更推荐：

- 在状态里使用 `RemainingSteps`
- 节点内部提前发现“步数快不够了”
- 主动输出部分结果、走降级路径或结束流程

优点：

- 可以优雅降级
- 能保留中间结果
- 更适合真实 agent 产品

### 11.3 `RemainingSteps`

`RemainingSteps` 是一个受 LangGraph 管理的特殊值。

它的作用是让节点知道：

- 当前距离递归上限还剩多少步

你可以基于它做：

- 低步数时停止继续探索
- 切换到 fallback 节点
- 输出“当前最佳答案”

这是构建稳定 agent 的关键技巧。

### 11.4 metadata 里还能拿到什么

文档里还提到可以通过 `config["metadata"]` 看到一些执行元信息，例如：

- 当前 step
- 当前 node
- 触发来源
- 执行路径
- checkpoint 命名空间

这对调试复杂图非常有价值。

---

## 12. Visualization：图可视化

LangGraph 支持把图可视化出来。

它的实际意义很大，因为图一旦复杂，仅靠代码很难快速看清：

- 从哪开始
- 有哪些分支
- 哪些地方会回环
- 哪些节点会收敛到终点

建议把可视化当成日常调试工具，而不是只在汇报时才看。

## 13. Observability and Tracing：可观测性与追踪

图式 agent 的难点不是“写出来”，而是“出问题时能不能解释”。

所以可观测性非常重要。

LangGraph 文档在这一节强调的方向是：

- 对执行路径做追踪
- 记录线程、节点、步骤信息
- 配合 LangSmith 观察实际运行过程

如果你的图进入生产，追踪能力几乎是必需品，不是锦上添花。

## 14. 初学者最容易踩的坑

### 14.1 把 state 当成普通输入输出对象

错误理解：

- 节点拿输入，吐输出，仅此而已

正确理解：

- 节点是在“读写一个共享状态空间”

### 14.2 忘记为累积字段配 reducer

表现通常是：

- 历史消息丢了
- 列表结果被后一个节点覆盖了

### 14.3 对副作用节点没有做幂等设计

结果可能是：

- 恢复执行时重复打外部 API
- 重复写入数据
- 重复扣费

### 14.4 把 `Command(resume=...)` 和普通重新调用混为一谈

这会导致：

- 你以为是在继续流程
- 实际却是从中断点恢复或从错误位置接着跑

### 14.5 图演进时直接重命名节点或状态 key

如果已有历史线程，这种改动风险不小。

## 15. 建议的学习顺序

如果你想系统学习 LangGraph，我建议按这个顺序：

1. 先只学 `StateGraph`、`START`、`END`、普通边
2. 再学 state schema 和 reducer
3. 再学 `messages`、`add_messages`、`MessagesState`
4. 再学条件边和 `Send`
5. 再学 `Command`
6. 再学 checkpoint、interrupt、resume
7. 最后学 runtime context、migration、cache、observability

原因是：

- 前三步解决“图怎么跑起来”
- 中间几步解决“图怎么变得像 agent”
- 最后几步解决“图怎么进入真实工程环境”

## 16. 一句话总结整页文档

Graph API 的本质不是“把函数串起来”，而是：

**用一套显式的状态机式图结构，来组织 agent 的状态、分支、恢复、并发、降级和可观测性。**

如果你掌握了下面这组关键词，基本就抓住这页文档主线了：

- `StateGraph`
- `State`
- `Reducer`
- `MessagesState`
- `START` / `END`
- Conditional Edges
- `Send`
- `Command`
- `interrupt` / `resume`
- `RemainingSteps`
- `Runtime context`

---

## 17. 面向实战的理解方式

你可以把 LangGraph 里的常见能力，直接映射为工程问题：

- `State`：我的 agent 在每一步共享什么上下文？
- `Reducer`：同一个字段被多次写入时怎么合并？
- `Edges`：下一步逻辑怎么决定？
- `Send`：怎么把一个任务拆成多路子任务？
- `Command`：怎么在一个节点里同时改状态和改流向？
- `interrupt/resume`：怎么做人审、暂停和恢复？
- `RemainingSteps`：怎么防止 agent 自己绕死？
- `Runtime context`：怎么把用户、环境、模型供应商等运行信息传进去？

只要你每次都用这套问题去看图设计，LangGraph 会比“抽象 API 文档”容易消化得多。

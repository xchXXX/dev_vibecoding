# 动态路由规则

## 固定关卡

- 需求接收
- `reader` 阅读委派
- `plan` 修订
- `plan` 冻结
- 动态拆单（按角色）
- 结果回收

## 角色优先分支

- 文档：`doc-curator`
- 测试：`test-verifier`
- 后端代码：`backend-implementer`
- 前端代码：`frontend-implementer`
- 运维：`ops-runbook`
- 审查：`reviewer`
- 只读排查：`reader`

## 决策矩阵

- 需求或上下文不完整：先派 `reader`，禁止直接进入实现工单
- 涉及契约、边界、README、runbook 变更：生成 `doc-curator` 工单
- 涉及行为回归风险：至少评估 `test-verifier` 工单
- 涉及实现落地：生成对应实现工单（后端或前端）
- 涉及部署、脚本、systemd、nginx、服务器操作：生成 `ops-runbook` 工单
- 只需方案研究或故障排查：可只生成 `reader` 工单，不进入代码实施
- 跨模块、超过 3 个写文件、状态机或数据契约变更：必须补 `dispatch_packet`

## reviewer 触发策略（复杂任务）

满足以下任一条件，默认触发 `reviewer`：

- 多个执行工单并行后需要合流验收
- 契约、状态机、数据结构或公共接口变更
- 关键验证失败后再次提交，需要裁决是否可继续
- 执行回执存在高风险、偏差或证据缺口

## 并行规则

- 写入集合互不重叠且无依赖：并行
- 下游依赖上游产物：串行
- 文档和测试可先行明确边界时，代码工单后置
- `reviewer` 通常在合流点串行执行，不与同一写入目标并行

## 回退矩阵

- 上下文不足 -> 回退 `reader`
- 方案不清 -> 回退 `planner`
- 风险未收敛 -> 回退 `reviewer`
- 验证不充分 -> 回退 `test-verifier`
- 出现越界写入或合同缺字段 -> `blocked` 并补齐合同后重派

## 默认推荐顺序

- 先方案
- 再文档
- 再测试
- 最后代码
- 最后由 `reviewer` 做合流审查（当触发条件满足时）

注意：默认推荐顺序不是强制流水线，关键看依赖与风险门禁。

- Windows 下不要把复杂 shell 逻辑优先写成一行命令；若命令同时含有多层引号、正则、here-string、长文本参数、跨 shell 转发、SSH 内嵌脚本或混合 repo/home 路径检索，应优先改写为 `.ps1` / `.py` 脚本块或分步执行。
- 复杂命令的目标是降低 quoting、分词、转义和 wrapper 差异，不是追求单行长度最短。
- `.cmd` 只作为简单参数入口；若参数中含有正则、引号、换行、here-string、长文本、复杂路径表达式或其他容易被 Windows batch 二次拆解的内容，不要继续走 `.cmd`，应直接调用对应 `.py` 或 `.ps1`。
- 需要把复杂命令临时落为 `.ps1` / `.py` 时，必须区分“正式真源脚本”和“一次性临时脚本”：
  - 可复用、被文档引用、被测试覆盖或被正式入口调用的脚本应保留在真源目录。
  - 一次性排障或临时分析脚本在完成后应及时清理，或隔离到明确的 sandbox / output / run artifacts 路径，不要污染正式脚本目录。
- 针对 Windows 平台噪音要单独判断：`ghost snapshot`、`NUL` 保留名索引失败等平台级异常，默认不直接等同于“当前任务命令失败”；只有用户实际执行的目标命令失败，才进入普通命令失败闭环。
- 若命令失败是由复杂 one-liner、自拼 quoting 或 `.cmd` 参数拆解触发，修复优先级应是“先重写命令结构”，而不是继续在原单行上盲目转义和重试。

- 对 Windows 宿主或 WSL 的任何 shell、terminal、test、build、install、script、toolchain、git、npm/pnpm/yarn、node、python/pip/uv/pytest、cargo、go、docker 命令，只要执行信号表明真实命令未成功，就视为命令失败；不要靠枚举错误文案判断是否触发。满足下述全部条件的 TDD 预期红不触发。
- TDD 预期红零触发必须同时满足：执行前明确声明 Red 阶段及预期失败类型、只运行最小目标测试、实际失败类型与预期一致。满足时不调用 Command Failure Memory launcher，也不执行 `record-failure`、`query-before-retry` 或 `record-success`。
- 任一预期红条件缺失、无法确认，或实际出现意外的命令、环境或基础设施错误时，必须按真实失败进入本闭环；不得用“TDD Red”掩盖另一条错误链路。
- 一旦命令失败，必须使用 WSL Python `command-failure-memory.py` 执行 `record-failure`。后端在 WSL 运行，每次显式传入 `--codex-home <已核实Windows目录的WSL路径>`；Windows PowerShell 仅发起 wsl.exe --exec 调用，不改用 Windows Python、batch 或 hook。
- 复杂参数使用 Python argv/JSON 输入，不为 batch 二次解析保留双轨逻辑。
- CFM 入口只按两个已知位置解析：先检查当前 workspace 的 `skills/command-failure-memory/scripts/command-failure-memory.py`；若不存在，再检查 `${CODEX_HOME:?set verified Windows Codex home WSL path}/skills/command-failure-memory/scripts/command-failure-memory.py`。候选入口必须先用 `test -f` 确认，不搜索 `.ai-harness/runtime`，也不猜测其他路径。
- 数据目录为已核实宿主 CODEX_HOME 下的 memories/command-failure-memory。本机核实为 `/mnt/c/Users/Laptop/.codex/memories/command-failure-memory`；无显式home即停止，不回退Linux HOME，不迁移、不复制、不另建经验库。
- 格式、active/archive 分层、容量策略和跨进程锁只能在原目录内演进；不复制、不另建、不让超限默默丢数据。
- 在任何 retry、rerun、重跑、重试或等价命令再次执行前，必须先执行 `query-before-retry`，不要盲目重试。
- 普通非零退出码不是切换执行环境的依据；不得离开 WSL 正常链重跑，也不增加自动重试或逐命令 preflight。
- 修复方案经重跑验证成功后，必须执行 `record-success`；需要审计经验库时执行 `inspect`。
- 该闭环默认启用，即使用户未显式提到 `command-failure-memory` skill 也一样。
- `ProjectId` 使用稳定仓库标识；`CommandText` 传实际失败命令及所属平台，不替换为记录失败的后端调用；`ErrorText` 优先传首行错误摘要，环境与路径来源按实际填写。
